> 입문자가 읽어도 이해되게 — '원자적으로 고쳤다'는 말이 왜 절반만 참일 수 있는지, 같은 버그를 다른 곳에서 세 번 만나는 게 왜 자연스러운 일인지, 그리고 '고친 코드에 테스트가 없다'는 상태가 왜 고치지 않은 것과 비슷한지 위주로.

## 1. 마지막 훈련 — 공개된 계정과 청구서 사이에 무엇이 서 있나

이 블로그에는 AI 초안 기능이 있다. 거친 메모를 넣으면 Claude가 정돈된 글의 초안을 만들어준다. 그리고 이틀 전, 방문자가 로그인해서 그 기능까지 써볼 수 있는 **데모 계정을 공개**했다.

공개 계정 + 돈이 나가는 기능. 이 조합이 안전하다고 믿은 근거는 방어선 네 겹이었다.

- 1층: IP당 시간당 10회 (서버 메모리에 있는 카운터)
- 2층: 계정당 시간당 '시도' 10회 (데이터베이스에 기록)
- 3층: 계정당 일일 20회 · 월간 200회 (데이터베이스에 기록)
- 4층: AWS 예산 알람 (한도를 넘으면 메일)

훈련의 질문은 하나다. **이 중 어느 것이 실제로 청구를 묶는가?**

### 어떻게 재나 — 경계에 세워놓고 밀기

이 훈련은 통과한 요청 수가 곧 실제 청구 건수다. 그래서 운영 서버를 때리지 않고 같은 코드가 도는 로컬 스택에 붙었다. 상한값은 운영과 동일하다.

시나리오는 '경계에 세워놓고 밀기'다. **"오늘 이미 19/20을 썼다. 남은 건 1회다"**를 데이터베이스에 만들어 놓고, 동시에 5발을 던진다. 상한이 총량을 묶는다면 성공은 정확히 1건이어야 한다.

> **🛠 전문가 노트** 동시에 던지는 게 핵심이다. 하나씩 순서대로 보내면 대부분의 상한은 잘 동작한다. 상한이 깨지는 건 거의 항상 '같은 순간에 여러 개가 들어올 때'다.

## 2. 남은 한도가 1회인데 5발이 전부 통과했다

▶ 실제 출력 — 동시 요청 5개 발사 (남은 한도는 1회)

```
  req code  elapsed(s)
  1 200 1.62
  2 200 2.00
  3 200 2.96
  4 200 1.98
  5 200 1.91
  전체 벽시계: 2.98s
  200(실제 Anthropic 청구): 5건   429(차단): 0건
  ai_usage(일일).count   = 24   ← 캡 20
  일일 캡 초과분          = 4건  ❌ 캡이 청구를 묶지 못했다
```

**5건 전부 통과했다.** 남은 한도가 1회인데 24/20이 됐다 — 20% 초과 청구. 여기서 200은 '요청 성공'이 아니라 **'실제로 돈이 나갔다'**는 뜻이다.

### 왜 — '원자적으로 고쳤다'는 기억이 절반만 맞았다

엿새 전에 같은 종류의 결함을 이미 한 번 고쳤다. 시간당 상한이 동시 요청에 뚫리길래, '먼저 올리고 그 결과로 판단하는' 방식으로 바꿨다. 그래서 머릿속에는 **"상한은 원자적으로 고쳤다"**로 저장돼 있었다.

틀렸다. 그때 고친 건 시간당 상한이고, **일일·월간 상한은 같이 안 고쳤다.** 이렇게 남아 있었다.

▶ 실제 출력 — 고치기 전 — 읽고 · 부르고 · 나중에 센다

```
if ai_usage.count_today(db, user_id) >= settings.ai_daily_cap:   # ① 읽고 판단
    raise HTTPException(429, ...)
...
markdown = generate_draft(...)                                   # ② LLM 호출 (수 초)
...
if provider == "claude":
    ai_usage.increment_today(db, user.id)                        # ③ 성공 뒤에 증가
```

증가(③)는 진짜로 원자적이었다. 데이터베이스가 보장해준다. 그래서 '원자적으로 고쳤다'는 기억이 생겼다. **하지만 원자적인 건 증가이고, 판단(①)은 그 앞에서 따로 하고 있었다.**

> **🔎 비유** 놀이기구 앞에서 표를 세는 사람과 태우는 사람이 다른 방에 있는 셈이다. 표 세는 사람은 정확하다. 문제는 손님이 '자리 있어요?'라고 물은 순간과 실제로 타는 순간 사이에 3초가 있고, 그 3초 동안 네 명이 더 물어봤다는 것이다. 전원 '있어요'라는 답을 들었다.

그리고 이 결함은 엿새 전에 고친 것보다 **나쁘다.** 시간당 상한은 읽기와 증가가 붙어 있어서 그 틈이 밀리초였다. 여기는 **읽기와 증가 사이에 LLM 호출이 들어 있다.** 훈련에서 실측한 틈은 위 출력의 벽시계 그대로 — **3.0초**다.

**⚠️ 함정**: 시간당 상한(10회, 원자적)이 위에서 뚜껑을 덮어주긴 한다. 하지만 그건 '안전하다'가 아니라 **'시간당 상한만큼은 넘칠 수 있다'**는 뜻이다. 일일 상한의 실질 상한은 20이 아니라 최대 20+9였다.

### 고친 것 — 먼저 예약하고, 안 되면 되돌린다

일일·월간도 시간당과 같은 방식으로 맞췄다. 먼저 원자적으로 1을 올리고, 그 결과값으로 판단하고, 통과 못 하면 예약을 되돌린다.

'성공만 센다'는 원래 의도는 **되돌리기로 보존**했다. 생성이 실패하면 예약을 취소한다. 취소는 실패 경로 셋에 흩어놓지 않고 한 곳(finally)에 뒀다. 하나만 빠뜨리면 사용자가 쓰지도 않은 한도를 잃는다.

> **🛠 전문가 노트** 되돌리기에 '0보다 클 때만 뺀다'는 조건을 붙였다. 없으면 취소가 겹칠 때 카운트가 음수로 내려가고, **음수는 다음 요청에게 '한도에 여유가 있다'로 읽혀** 상한 자체가 무너진다. 안전장치를 고치다가 안전장치를 뚫는 흔한 방식이다.

▶ 실제 출력 — 같은 훈련을 그대로 재실행

```
  req code  elapsed(s)
  1 200 1.98
  2 429 0.09
  3 429 0.11
  4 429 0.11
  5 429 0.10
  200(실제 Anthropic 청구): 1건   429(차단): 4건
  ai_usage(일일).count   = 20   ← 캡 20
  일일 캡 초과분          = 0건  ✅ 캡 안
```

차단된 4건은 **0.1초 안에** 끝났다. LLM 호출까지 가지 않았으므로 청구도 없다. 그게 이 수정의 요점이기도 하다. 막는 것과 '돈 나간 뒤에 막는 것'은 다르다.

월간 경계도 따로 재봤다. 199/200에서 동시 5발 → 1건 통과, 4건 차단, 월간 합계 정확히 200.

## 3. 예산 두 개가 같은 달을 보며 $17.78과 $0.00을 보고했다

3층까지 확인했으니 4층(AWS 예산 알람)을 보러 갔다. 예산이 두 개 있었다.

▶ 실제 출력 — 같은 계정 · 같은 달 · 다른 대답

```
예산                     상한      실사용         알림 상태
My Monthly Cost Budget   $10/월    $17.783 (178%)  ACTUAL>85%  ALARM
                                                   ACTUAL>100% ALARM
My Zero-Spend Budget     $1/월     $0.00           ACTUAL>$0.01 OK
```

같은 계정, 같은 달이다. 차이는 딱 하나 — **크레딧을 비용으로 세는가.** 비용을 종류별로 쪼개보니 답이 나왔다.

▶ 실제 출력 — Cost Explorer를 RECORD_TYPE으로 분해

```
Usage             17.7836033411
Credit           -17.7834727487
Bundled Discount  -0.0001312421
Tax                0
                 ─────────────
순액              ≈ 0.0000
```

Zero-Spend 예산은 크레딧을 반영하는 설정이라 사용액이 상계돼 $0.00으로 읽는다. Monthly 예산은 크레딧을 빼지 않아 $17.78을 본다. 둘 다 거짓말은 아니다.

**⚠️ 함정**: 문제는 **어느 쪽이 무슨 일을 하기로 되어 있었나**다. '쓸 의도가 없었는데 돈이 나가고 있다'를 잡는 게 Zero-Spend 예산의 존재 이유인데, 이 계정은 유한한 크레딧을 태우는 중이다. 즉 그 예산은 **정확히 그것이 필요한 기간 동안 반드시 침묵한다.** 크레딧이 0이 되는 순간에야 입을 연다.

한 달 전에 '청구서가 $0'과 '안 쓰고 있다'는 다르다는 걸 이미 배워서 적어뒀었다. 그런데 **그 교훈이 정작 가드레일 설정에는 반영되지 않은 채 남아 있었다.** 오늘의 주제가 여기서도 반복된다. 배운 것과 적용된 것은 다르다.

한편 $10 예산은 **실제로 울렸다.** 85%·100% 둘 다 경보 상태로 증거가 남아 있다. 그래서 이 훈련이 답한 것과 못 답한 것이 갈린다.

- 답함: 예산 알람은 구성돼 있고 실제로 발동했다 (상태가 증거다)
- 못 답함 — 그 메일함을 사람이 보는가

> **🛠 전문가 노트** #19의 '설정했다 ≠ 동작한다'의 다음 단계다. **'발동했다 ≠ 사람에게 닿았다'.** 이건 코드로 증명할 수 없다. 그래서 정직하게 '못 답함'으로 남긴다.

## 4. 그 감시를 검사했더니 거짓말을 하고 있었다

예산 상태를 매번 콘솔에서 확인할 수는 없으니, 점검 스크립트에 '예산 확인' 항목을 새로 넣었다. 그리고 넣자마자 **그것에 고장을 주입해봤다.**

> **🔎 비유** 화재경보기를 달았으면 라이터로 켜봐야 한다. 이번엔 한 걸음 더 갔다. 경보기의 배선을 끊어놓고, 그때 경보기가 뭐라고 말하는지 봤다.

▶ 실제 출력 — 고장 주입 4종 — 무엇을 말했나

```
주입                        처음 나온 말                  사실
자격증명 실패                "예산을 못 읽었다"             맞음
python3이 깨짐               "예산이 0개다 —              예산 2개 있었다
                             청구서 폭주를 알려줄
                             장치가 없다"
목록은 읽히고 알림만 실패    "ACTUAL 알림이 없다"          못 읽은 것
읽었는데 진짜 0개            "예산이 0개다"                맞음
```

두 번째가 특히 나쁘다. 예산 개수를 파이썬으로 셌는데, 그 명령이 실패하면 0으로 치도록 해뒀다. 그래서 **해석기가 죽은 것이 "가드레일이 없다"는 사실 주장으로 승격**됐다.

**⚠️ 함정**: 감시가 틀리게 말하는 건 감시가 없는 것보다 나쁘다. 없으면 모르는 줄 알지만, 틀리면 **아는 줄 안다.** 저 메시지를 보고 예산을 다시 만들었으면, 같은 계정에 예산이 네 개가 됐을 것이다.

이 병을 만난 게 이번이 세 번째다. #18에서 빈 값을 초록으로 보고했고, #21에서 증상 서술이 틀렸다. 그래서 이번엔 조건을 고치는 대신 **그 경로 자체를 없앴다.** 파이썬 없이 AWS 명령의 기능과 awk만 쓴다. 둘 다 없으면 애초에 조회가 안 되므로 '못 읽었다'로 정직하게 떨어진다.

> **🛠 전문가 노트** 같은 버그를 세 번 만나면 그건 실수가 아니라 **구조**다. 그때는 그 자리를 고치는 게 아니라, 그 실수를 할 수 있는 경로를 없애는 쪽이 맞다.

## 5. 오후 — 코드를 처음부터 훑기

훈련 넷이 끝났다. 훈련은 '무너뜨려 보고 고치는' 것이다. 이제 남은 건 '무너뜨릴 곳이 더 있나 읽어보는' 것이었다. 질문은 하나였다 — **훈련이 건드리지 않은 경로에도 같은 병이 남아 있나.**

### 무인증으로 서버 메모리에 20MB를 밀어넣을 수 있었다

서버에는 '요청 본문이 6MB를 넘으면 거부한다'는 상한이 있다. 작은 서버라 큰 요청 몇 개면 메모리가 바닥나기 때문이다.

그런데 그 검사가 **요청에 붙은 '크기 신고서'만 보고 있었다.** HTTP에는 크기를 미리 신고하지 않고 흘려보내는 방식이 따로 있다. 신고서가 없으면 검사가 아예 안 돌았다.

▶ 실제 출력 — 같은 20MB를 두 가지 방식으로 (고치기 전)

```
A) Content-Length: 20000000   → 413  (0.012초)   차단
B) Transfer-Encoding: chunked → 422  (7.7초)     우회
   B에서 20,002,488바이트가 전부 앱까지 들어와 메모리에 머문 뒤
   JSON 파싱 단계에서야 튕겼다.
```

B가 우회다. 그리고 이건 **로그인처럼 로그인하지 않아도 부를 수 있는 주소**에서도 된다. 누구나, 몇 번이든.

앞단(CDN·방화벽)도 못 막는다. CDN 함수는 본문을 아예 볼 수 없어서 같은 신고서 검사밖에 못 하고, 방화벽의 본문 크기 규칙은 '감시만' 상태로 내려가 있다(그 규칙을 켜면 8KB가 넘는 이미지 업로드가 전부 죽는다). 그래서 방어는 앱에 있어야 했다.

고친 방식은 **'세면서 받기'**다. 신고서가 있으면 본문을 한 바이트도 안 읽고 판정하고, 없으면 상한까지만 받으면서 세다가 넘는 순간 끊는다.

▶ 실제 출력 — 고친 뒤 같은 두 발

```
A) Content-Length  → 413  (0.012초)
B) chunked         → 413  (0.098초)     ← 7.7초에서
```

> **🛠 전문가 노트** 이 수정의 진짜 위험은 우회가 아니라 **정상 요청을 조용히 망가뜨리는 것**이다. 본문을 검사하려고 먼저 읽어버리면, 그걸 앱에 되돌려주지 못할 때 모든 글쓰기가 깨진다. 그래서 '막혔나'보다 '멀쩡한 게 그대로 지나가나'를 더 오래 쟀다.

▶ 실제 출력 — 되돌려주기(replay)가 멀쩡한가

```
chunked 정상 JSON 로그인 → 401   (신고서 방식과 똑같은 답)
chunked 5MB(상한 이하)   → 422   (본문이 끝까지 도착해 파서까지 감)
```

### 업로드에만 사용량 상한이 없었다

글 30/시간, 댓글 20/시간, AI 10/시간, 결제 20/시간. 전부 상한이 걸려 있다. **이미지 업로드만 없었다.** 12연발이 전부 성공했다.

하필 이 경로는 한 번에 5MB를 클라우드 저장소에 올리고 CDN으로 내보내는 **돈이 붙는 쓰기**다. 그리고 하필 이틀 전에 공개한 데모 계정이 그대로 부를 수 있었다.

**⚠️ 함정**: 같은 날 AI 비용 상한을 조여놓고 이쪽을 열어둔 셈이다. 방어선을 세울 때 '비슷한 것 전부'를 훑지 않으면, 가장 눈에 띄는 것만 잠그고 끝난다.

## 6. 그리고 여기서 작업이 끊겼다

두 수정을 코드에 넣고, 이제 테스트를 쓰고 커밋할 차례였다. **그 자리에서 쓰던 도구에 장애가 나서 세션이 끊겼다.** 그래서 다음 날 아침의 시작 상태는 이랬다.

전체 테스트를 돌려보니 **146개 통과.** 그런데 그건 수정을 하기 전과 똑같은 숫자였다. 당연하다. 테스트를 쓰기 직전에 멈췄으니까.

> **🔎 비유** 자물쇠를 새로 달다가 전기가 나간 것이다. 자물쇠는 문에 붙어 있는데, 그게 잠기는지 확인하는 절차는 점검표에 아직 한 줄도 없다.

여기서 배운 건 '왜 안 했나'가 아니다. 하려던 참이었으니까. 배운 건 **중단은 예고 없이 온다**는 것이고, 그래서 **끊긴 자리가 하필 가장 취약한 자리**라는 것이다. 수정은 디스크에만 있고, 그게 맞다는 증거는 아직 없고, 되돌릴 방법도 없다. 명령 하나면 하루치가 사라진다.

> **🛠 전문가 노트** 그래서 습관 하나를 바꿨다. 고친 직후에 **일단 커밋을 하나 찍어둔다.** 테스트는 그다음에 붙이면 된다. 완성된 것만 커밋하려다 미완성인 채로 잃는 것보다, 미완성을 커밋해두고 이어가는 쪽이 항상 싸다.

그래서 다음 날 오후의 절반은 그 자리를 이어받는 데 썼다. 테스트를 쓸 때 이 저장소의 규칙은 하나다. **고치기 전 코드에서 실제로 실패하는지 확인한다.** 안 하면 그 테스트가 뭘 잡는지 모른다.

▶ 실제 출력 — 고치기 전 코드로 되돌려 실행

```
CHUNKED ->        422        ← 우회가 실재했다는 증거
CONTENT-LENGTH -> 413        ← 이 경로는 원래 막고 있었다(대조군)
업로드 31번째:    assert 200 == 429   ← 상한이 없었다
```

본문 상한 테스트는 7개를 썼다. 그중 4개는 '조각난 요청'을 다룬다. 테스트 도구가 본문을 한 덩어리로 합쳐 보내버려서, 조각 경계에서의 동작은 미들웨어를 직접 불러서 검증해야 했다. 조각 순서가 보존되는지, 상한을 넘는 순간 나머지를 안 읽는지, 딱 상한과 같은 크기는 통과하는지.

### 그 수정이 CI를 빨간불로 만들고 있었다

커밋하기 전에 코드 스타일 검사를 돌렸다.

▶ 실제 출력 — ruff check

```
I001 [*] Import block is un-sorted or un-formatted
  --> app/main.py:10:1
Found 2 errors.
```

어제 수정하면서 새 import를 아무 데나 끼워넣었다. 이 검사는 자동 배포의 관문이다. **고친 코드가 검사를 깨뜨리고 있었다.**

> **🛠 전문가 노트** 이게 커밋 전에 잡혔다는 게 이 검사의 값이다. 검사를 로컬에서 돌리는 데 3초 걸린다. 안 돌렸으면 푸시하고 나서 빨간 메일을 받고, 뭐가 깨졌는지 다시 찾았을 것이다.

## 7. 훈련이 지나간 자리만 고쳐져 있었다

이틀 전 카오스 훈련에서 배운 게 있다. 바깥(데이터베이스·저장소)이 죽었을 때 서버가 **500 오류를 평문으로** 뱉으면, 화면은 JSON을 기대하므로 파싱조차 못 하고 사용자는 이유를 모른 채 빨간 에러만 본다. 그래서 그 두 곳을 503으로 고쳤다.

오늘 같은 병을 한 군데 더 찾았다. 사용자가 자기 AI 키를 맡기면 암호화해서 보관하는데, **서버의 암호화 키가 바뀌면 그 암호문을 못 푼다.** 그때 무슨 일이 일어나는지 재봤다.

▶ 실제 출력 — 예전 키로 저장 → 서버 키 교체 → 초안 요청

```
cryptography.fernet.InvalidToken
  → 500 Internal Server Error  (text/plain)
```

아무데서도 안 잡히고 있었다. 이틀 전에 고친 것과 **완전히 같은 병**인데, 훈련이 그 경로를 지나가지 않아서 그대로 남아 있었다.

**⚠️ 함정**: 훈련은 '내가 죽여본 것'만 알려준다. 데이터베이스를 죽여봤고 저장소를 죽여봤으니 그 둘은 고쳤다. **죽여보지 않은 세 번째는 그대로다.** 훈련의 커버리지를 훈련의 결론으로 착각하면 안 된다.

503으로 바꾸면서 메시지도 손봤다. 원인은 서버 쪽이지만, **사용자가 할 수 있는 일이 있다** — 설정에서 키를 다시 등록하면 된다. 그걸 알려주지 않으면 사용자는 기다리는 것 말고 할 게 없다.

### 한쪽만 고쳐진 알림 배지

비슷한 모양이 하나 더 나왔다. 알림 목록에는 '지금 이 사용자가 볼 수 있는 글만' 조건이 걸려 있다. 주석에 "글이 비공개로 바뀌면 제목이 새던 것을 고쳤다"고 적혀 있었다.

그런데 **종 아이콘 옆의 숫자에는 그 조건이 없었다.**

▶ 실제 출력 — 구독 중인 글쓴이가 글을 비공개로 내리면

```
items  = []      (목록은 비었다)
unread = 1       (배지는 1)
```

사용자는 **눌러도 사라지지 않는 배지**를 보게 된다. 조건을 한 번만 만들어서 두 곳이 같은 것을 쓰게 고쳤다.

> **🛠 전문가 노트** 같은 판단을 두 군데서 따로 만들면 반드시 한쪽만 고쳐진다. 고칠 때 '이 판단을 쓰는 곳이 또 어디지?'를 묻는 습관이 이걸 막는다. 오늘 나온 결함 넷 중 셋이 이 모양이었다.

## 8. 훑었는데 아무것도 안 나온 곳

결함이 안 나온 곳도 적어둔다. 안 적으면 다음에 또 처음부터 읽는다. 그리고 솔직히, 이쪽이 훨씬 많았다.

- 저장형 XSS — 글 본문에 <script>를 넣어도 렌더러가 글자로만 취급한다. 코드에 '이 옵션을 켜지 마라'는 경고까지 적혀 있었다
- SSRF: 사용자가 지정하는 유일한 주소(자기 LLM 엔드포인트)는 https + 공인 IP만 허용하고, 리다이렉트 추종도 꺼져 있다
- 권한 우회 — '볼 수 있는 글' 판단이 함수 하나로 모여 있고 목록·검색·연재·댓글·알림이 전부 그걸 쓴다
- SQL 주입 — 검색어는 파라미터로 넘어가고 와일드카드 문자도 이스케이프된다
- 결제: 행 잠금 + 금액 대조 + 중복 승인 멱등 처리. 더블클릭으로 회계가 어긋나지 않는다
- 계정 선점 — 미인증 상태로 남의 이메일을 선점하는 경로가 막혀 있다

도구 검사도 전부 돌렸다.

▶ 실제 출력 — CI가 도는 검사를 로컬에서 그대로

```
gitleaks (커밋 212개 전체)   0건
shellcheck (스크립트 전부)   0건
pip-audit (백엔드 의존성)    0건
npm audit (프론트 의존성)    high 2건 = 같은 것 하나
                             (판단 기록됨 · 만료 10-26 · 아직 유효)
terraform fmt · validate     통과
런북 드리프트                어긋난 곳 없음
프론트 lint · test · build   통과 (18 tests)
```

## 9. 오늘 배운 것

### ① '원자적으로 고쳤다'는 문장은 주어를 확인해야 한다

증가가 원자적인 것과 '판단+증가'가 원자적인 것은 다르다. 그리고 그 둘 사이에 네트워크 호출이 들어 있으면, 틈은 밀리초가 아니라 초 단위가 된다.

### ② 같은 버그를 세 번 만나면 그건 구조다

'실패를 0으로 읽는' 버그를 세 번째로 만났다. 그때는 조건문을 고치는 게 아니라 그 실수를 할 수 있는 경로를 없애는 쪽이 맞다.

### ③ 훈련의 커버리지가 훈련의 결론은 아니다

죽여본 것만 고쳐진다. 카오스 훈련이 데이터베이스와 저장소를 지나갔으니 그 둘은 고쳐졌고, 지나가지 않은 세 번째는 이틀 동안 그대로 있었다.

### ④ 중단은 예고 없이 오고, 끊긴 자리가 가장 취약하다

도구 장애로 하필 '고쳤지만 아직 증명하지 않은' 지점에서 멈췄다. 그 상태는 '고쳤다'가 아니라 **'지금은 맞다'**에 가깝다. 수정은 디스크에만 있고, 그게 맞다는 증거도 되돌릴 방법도 없다.

그래서 완성될 때까지 커밋을 미루지 않기로 했다. 미완성을 커밋해두고 이어가는 쪽이 완성만 커밋하려다 미완성인 채로 잃는 것보다 항상 싸다.

### ⑤ 판단을 두 군데서 따로 만들면 반드시 한쪽만 고쳐진다

알림 목록과 알림 배지, 캡 판단과 캡 증가. 오늘 나온 결함 대부분이 이 모양이다.

## 10. 오늘의 숫자

▶ 실제 출력 — 전 → 후

```
테스트      140 → 146 → 156     (훈련 +6, 심층검사 +10)
커버리지    78.95%(훈련 직후) → 80.78%
ruff        실패(2건) → 통과
새 테스트 16개 중 7개는 고치기 전 코드에서 실제로 실패하는 것을 확인
  (훈련 6개 중 3개 · 심층검사 10개 중 4개)
나머지 9개는 새 결함을 잡는 게 아니라 계약을 못박는 것이다 —
그렇게 적어두지 않으면 다음 수정 때 조용히 깨진다.
```

실제로 쓴 돈은 Anthropic 호출 7건이다(가장 싼 모델, 한 줄 메모). 차단된 10건은 LLM까지 가지 않아 무료다. 그게 이 수정의 요점이기도 하다.

## 11. 정직하게 남기는 것

오늘도 못 답한 것들이 있다. 답한 척하는 것보다 적어두는 게 낫다.

- 예산 알람이 **사람에게 닿는가** — 발동한 건 증거가 있지만, 그 메일함을 여는지는 코드로 증명할 수 없다
- Zero-Spend 예산의 크레딧 눈가림 — 설정을 바꾸면 의미가 생기지만, 그러면 다른 예산과 사실상 같은 걸 두 번 보는 셈이다. 무엇을 알고 싶은지부터 정해야 한다
- 예산 두 개가 코드 밖(콘솔)에 있다. 다른 드리프트와 같은 성질의 위험이다. 다만 코드로 옮기면 알림 수신 주소를 코드에 박게 된다
- 업로드 상한이 IP 기준이다. 여러 IP로 몰리면 얇다. 계정 기준으로 가려면 테이블이 하나 더 필요하다
- 암호화 키 교체 상황에서 사용자가 시간당 '시도' 한도를 하나 잃는다. 서버 쪽 사고인데 사용자가 손해를 본다. 다만 '시도는 실패도 센다'가 의도된 계약이라, 곁다리로 바꾸는 게 더 나쁘다고 판단했다

**오늘의 커밋**: 4개 — 비용 캡 수정, 감시 수정, 심층검사 수정, 기록

**추가한 테스트**: 16개 (전부 무엇을 잡는지 확인함)

**남은 것**: SES 운영 접근 — 지금은 샌드박스라 인증한 주소로만 메일이 나간다
