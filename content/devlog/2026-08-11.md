## 1. 아침 — 업로드를 살리고 있던 규칙이 코드에 없었다

이 블로그는 인프라를 전부 코드로 관리한다(Terraform). 서버·네트워크·CDN 설정이 파일로 적혀 있고, 그 파일이 곧 진실이다. 그래야 서버가 통째로 날아가도 되살릴 수 있다.

그런데 오늘 확인해 보니 **방화벽(WAF) 하나가 그 바깥에 있었다.** CloudFront를 만들 때 AWS가 자동으로 붙여준 물건이라 코드에 없었고, 더 중요한 건 그 위에 내가 **콘솔에서 손으로 예외 두 개를 걸어뒀다**는 것이다.

▶ 실제 출력 — 콘솔에만 있던 예외 두 개 (terraform import 후 코드로 회수한 내용)

```
rule_action_override {
  name = "SizeRestrictions_BODY"
  action_to_use { count {} }      # 큰 본문을 차단하지 않고 세기만 한다
}
rule_action_override {
  name = "CrossSiteScripting_BODY"
  action_to_use { count {} }      # 이미지 바이트를 XSS로 오인하던 규칙
}
```

이 두 줄이 없으면 **이미지 업로드가 막힌다.** 사진 파일의 바이트열이 우연히 공격 패턴처럼 보여서 차단되기 때문이다. 즉 블로그의 핵심 기능 하나가 '코드 어디에도 안 적힌 설정' 위에서 돌고 있었다.

> **🔎 비유** 집 열쇠를 현관 매트 밑에 두고 사는 것과 비슷하다. 지금은 잘 들어간다. 그런데 이사 계획서(코드)에는 '열쇠는 매트 밑'이라는 말이 없다. 이사하는 날, 계획서대로만 하면 문이 안 열린다.

terraform import로 이 WebACL을 코드 관리로 가져왔다. 한 가지 조심할 게 있었다.

**⚠️ 함정**: 이 WAF는 CloudFront에 딸려 온 것이라 **공짜**다. 그런데 코드로 가져오면서 실수로 '지우고 새로 만들기'가 되면, 새로 만든 WAF는 **월 요금이 붙는 별개 상품**이 된다. 그래서 계획(plan)에 destroy나 replace가 한 글자라도 보이면 멈추기로 하고, 코드에도 prevent_destroy를 걸었다.

> **🛠 전문가 노트** import는 '이미 있는 것을 코드의 관리 아래로 데려오는' 명령이다. 새로 만들지 않는다. 인프라를 코드로 옮길 때 처음부터 다시 만드는 게 아니라 import부터 하는 이유가 이것이다. 돌고 있는 것을 끊지 않는다.

## 2. 한 번 울리고 스스로 꺼지는 알람

이 저장소에는 규칙이 하나 있다. **백엔드를 먼저 배포하고 프론트를 나중에 배포한다.** 순서를 뒤집으면 프론트가 아직 존재하지 않는 API를 부르고, 화면이 깨진다.

그래서 '한 번에 백엔드와 프론트가 같이 바뀌었으면 프론트 배포를 막는' 게이트를 만들어 뒀었다. 그리고 어제 그 게이트가 실제로 두 번 울렸다. 잘 동작하는 것처럼 보였다.

▶ 실제 출력 — 어제와 오늘의 Actions 기록 — 같은 프론트 변경이 결국 나갔다

```
run #59  09:37Z  Deploy Frontend   ❌  백엔드 동시 변경 게이트가 막음
run #60  10:38Z  Deploy Frontend   ❌  같은 이유로 또 막음
...
run #61  (오늘)  Deploy Frontend   ✅  통과 — 그런데 백엔드는 여전히 미배포였다
```

왜 통과했을까. 게이트가 보는 것은 **'이번 푸시의 변경분'**이었기 때문이다. 어제 푸시에는 백엔드 커밋이 섞여 있어서 막혔다. 오늘 푸시는 문서와 의존성만이라 '백엔드 변경 없음'으로 읽혔고 — 그래서 **어제 막혔던 그 프론트가 오늘 얹혀서 나갔다.**

**경고를 한 번 울리고 스스로 해제되는 알람이었다.** 그리고 그게 가장 나쁜 종류다. 울렸다는 사실이 '이 장치는 잘 동작한다'는 근거로 남기 때문이다.

> **🔎 비유** 화재경보기가 연기를 감지해 울렸다. 그런데 다음 날 아침이 되면 저절로 꺼지고 '해결됨'으로 표시된다. 불은 그대로다. 경보기가 없는 것보다 나쁜 이유는, 울린 적이 있다는 이유로 사람들이 그걸 믿기 때문이다.

제대로 고치려면 '지금 서버에 떠 있는 백엔드가 어느 커밋인가'를 알아야 하는데, 그 기록이 저장소에도 서버에도 AWS에도 없었다. 그리고 **백엔드 배포는 이미 100% 수동**이다. 프론트만 자동일 이유가 없었다. 그래서 자동을 없앴다.

**결정**: deploy.yml에서 on: push 제거. 이제 프론트는 사람이 Run workflow를 눌러야 나간다

> **🛠 전문가 노트** 여기서 배운 것: 게이트를 '변경분(diff)'으로 판단하면 **상태**를 판단할 수 없다. diff는 '이번에 무엇이 바뀌었나'고, 배포는 '지금 무엇이 떠 있나'의 문제다. 질문이 다르면 답도 다르다.

## 3. 감시가 280번 초록이었는데, 파일 두 개는 12일 전에 사라져 있었다

이 저장소에는 매시간 도는 감시 스크립트가 있다. 백업이 쌓이는지, 서버가 켜져 있는지, 메일이 나가는지, 그리고 **업로드한 이미지가 무사한지**를 본다.

이미지 검사는 이렇게 생겼었다. 원본 폴더와 사본 폴더의 파일 개수를 비교한다. 그런데 원본이 0개일 때 이 검사는 '확인할 것 없음'으로 넘어갔다.

▶ 실제 출력 — 고치기 전 판정 — 원본 0개를 '정상'으로 읽었다

```
src=0  dst=2
✅ 업로드 이미지 없음(확인할 것 없음)
```

**원본 0개 / 사본 2개는 '이미지가 없다'가 아니라 '이미지를 잃었다'는 뜻이다.** 사본은 서버를 끌 때 미러링해 둔 것이니, 사본만 있고 원본이 없다는 건 원본이 지워졌다는 말이다.

실제로 그랬다. 파일 두 개가 2026-07-30 05:03 UTC에 지워졌고, 오늘(08-11)까지 **12일 동안 약 280번의 감시가 전부 초록이었다.**

▶ 실제 출력 — 복구 — 버전 관리가 켜져 있어서 '삭제 표식'만 지우면 되살아난다

```
$ aws s3api list-object-versions --bucket blogplafromops --prefix uploads/ \
    --query "DeleteMarkers[?IsLatest==\`true\`].[Key,VersionId]" --output text
uploads/....png   3Hkq1Z...
uploads/....png   9Ttx0M...
$ aws s3api delete-object --bucket ... --key ... --version-id ...
  → 두 파일 모두 복구. 만료 정책이 없어 시한도 없었다.
```

> **🔎 비유** 휴지통에 들어간 파일을 12일 동안 아무도 안 본 것과 같다. 다행히 이 휴지통은 자동으로 비워지지 않게 해 뒀다. 그게 아니었으면 오늘 발견해도 늦었다.

고칠 때 한 번 더 미끄러졌다. 처음엔 '원본 0 · 사본 >0이면 실패'로 바꿨는데, **서버를 끄는 절차의 미러링에는 삭제 옵션이 없어서 사본은 절대 줄지 않는다.** 그러면 사용자가 이미지를 정상적으로 전부 지운 날부터 감시가 영원히 빨간불이 된다.

**⚠️ 함정**: **영원히 빨간불인 검사는 없는 검사와 같다.** 사람이 이틀이면 무시하기 시작한다. 그래서 판정 기준을 개수가 아니라 **'삭제 표식이 있는가'**로 바꿨다. 정상적으로 비운 것과 지워진 것을 그때 처음으로 구분할 수 있게 됐다.

그리고 같은 검사가 복원 훈련 스크립트에도 복사돼 있었다. 거기도 같이 고쳤다. 어제 편의 주제(고친 자리 옆의 안 쓸린 입구)가 오늘 아침에 바로 또 나온 것이다.

## 4. 검사를 여섯 번 돌렸다

여기서부터 하루의 본론이다. 성격이 다른 검사를 여섯 번, 서로 겹치지 않게 돌렸다. 각 검사가 **자기만 잡은 것**이 있었다는 게 이 절의 요점이다.

### 4-1. 공백 검사 — '없는 것'을 찾는다

코드를 보는 게 아니라 **코드에 없는 것**을 찾는 검사다. 여기서 나온 게 앞의 이미지 건이고, 또 하나가 이거였다.

▶ 실제 출력 — 문법 검사가 폴더 한 겹을 안 보고 있었다

```
# 검사 코드
for f in scripts/*.sh; do bash -n "$f"; done
# scripts/*.sh 는 하위 디렉터리를 보지 않는다
검사된 파일: 9개
빠진 파일  : scripts/lib/ec2.sh   ← 스크립트 5개가 공유하는 입구
```

웃긴 건 **바로 아래 줄에 '이 구멍은 닫았다'는 주석이 있었다**는 것이다. 옆의 다른 검사는 이미 같은 이유로 고쳐 뒀는데, 이 줄만 안 쓸려 있었다. 고쳐서 9개 → 10개가 됐다.

### 4-2. 교차검증 — 오늘 쓴 코드가 정말 맞는가

에이전트 여럿에게 **서로의 결론을 반박하게** 시켰다. 여기서 내가 배운 게 하나 있다.

내가 사용자에게 "이 다섯 건은 전부 사실입니다"라고 말했는데, 반박 담당이 두 건을 깎았다. '상한이 없다'고 했지만 다른 상한이 실질적으로 막고 있었고, '집계가 틀어진다'고 했지만 그 함수는 0/0이면 애초에 아무것도 안 했다.

> **🛠 전문가 노트** **한 명이 찾고 한 명이 반박하는 구조가 실제로 값을 한다.** 찾는 쪽은 '문제를 찾는 게 임무'라서 과장하는 방향으로 기울고, 반박하는 쪽은 그 반대다. 둘을 붙여야 남는 게 사실에 가깝다. 나 혼자 확신하면 그냥 확신인 채로 나간다.

### 4-3. 병목 — 논쟁하지 말고 재라

성능 검사에서 예측이 여럿 나왔다. 그래서 서버를 켜고 **실제로 쟀다.** 예측 두 건이 깎였고, 대신 예측보다 훨씬 큰 게 나왔다.

▶ 실제 출력 — 실측 — 이미지 업로드 요청 하나가 API 전체를 멈추던 자리

```
업로드 라우트: S3 전송이 끝날 때까지 DB 커넥션을 쥐고 있었다
최악 추정      : 요청 1개가 약 51초 동안 커넥션 1개 점유
커넥션 풀      : 15개 → 동시 업로드 몇 개면 사이트 전체가 대기
고침: DB 작업을 먼저 커밋하고, 그 다음에 S3로 보낸다
```

같은 방식으로, 관리자 화면이 1초마다 서버 상태를 물어보면서 **CPU 크레딧을 하루 29개씩 태우던 것**도 찾았다. 이 서버(t2.micro)는 CPU를 '크레딧'으로 쓰는 종류라, 크레딧이 마르면 서버가 통째로 느려진다.

> **🔎 비유** 전기요금이 이상하다고 생각될 때, 사람들은 보통 냉장고와 에어컨을 두고 논쟁한다. 계량기를 보면 5분이면 끝난다. 오늘 잰 것 중 제일 큰 건 아무도 얘기하지 않던 쪽에 있었다.

### 4-4. 동료 리뷰 — 주석과 코드가 반대였다

사람이 코드를 읽듯 읽는 검사다. 오늘 제일 아픈 게 여기서 나왔다. **내가 아침에 쓴 코드**였다.

▶ 실제 출력 — 주석은 '커밋 전에'라고 하고, 코드는 커밋 뒤에 있었다

```
# 커밋 전에 로컬 변수로 떠둔다 (커밋 후에는 객체가 만료돼 재조회가 일어난다)
db.commit()
uid = user.id          # ← 주석이 하지 말라는 바로 그 자리
```

주석이 정확히 옳았고, 코드가 그 반대였다. 이런 게 특히 나쁜 이유는 **주석이 잘 쓰여 있을수록 읽는 사람이 코드를 안 보게 되기 때문**이다.

이 라운드에서 하나 더 나왔다. 인프라 코드에 CDN의 ID가 문자열로 박혀 있었는데, 그러면 CDN을 다시 만드는 순간 **사이트 전체가 403**이 된다. 참조로 바꿨고, 계획을 돌려보니 '변경 없음'이었다. 위험은 0이고 얻는 건 재생성 안전성이다.

> **🛠 전문가 노트** 작성자 변론(내가 쓴 코드를 내가 옹호하게 하는 역할)도 붙였는데, 이게 내 수정안을 한 번 교정했다. 커밋 위치를 한 줄 위로 올리려 했더니 '그러면 재조회가 일어나서 1회용 초대 링크가 사라질 수 있다'고 했다. 맞는 말이라 위치를 바꿨다.

### 4-5. 동적 분석 — 실제로 돌려봤더니

읽는 게 아니라 **띄워서 실제로 요청을 보내는** 검사다. 오늘 제일 위험한 게 여기서 나왔다.

▶ 실제 출력 — 이메일 형식이 어긋난 계정 하나가 관리자 화면 전체를 죽였다

```
$ python scripts/create_user.py a@test.local   # 예약 TLD — 검증이 없었다
  ✓ 계정 생성 완료
$ GET /api/admin/users
  500 Internal Server Error
  이유: 응답 검증이 EmailStr이라 그 한 행에서 터진다.
  그리고 그 계정을 지울 수 있는 유일한 화면이 바로 이 목록이다.
  → 복구 경로가 psql 직접 접속뿐이었다.
```

**한 행이 전체를 죽였고, 그 전체가 유일한 복구 수단이었다.** 두 군데를 고쳤다. 들어오는 입구(계정 생성 스크립트)에서 형식을 검사하고, 나가는 출구에서는 검사를 뺐다.

> **🔎 비유** 명부에 이름이 잘못 적힌 사람이 한 명 있다고 해서 명부 전체를 못 펴게 하면 안 된다. 특히 그 잘못을 고치려면 명부를 펴야 할 때는.

그리고 같은 라운드에서 이걸 발견했다.

▶ 실제 출력 — 오늘 넣은 로그가 한 줄도 안 나가고 있었다

```
$ docker compose logs backend | grep "AI 초안 완료"
(0건)
이유: 저장소 어디에도 로깅 설정이 없어서
  root 로거 레벨 = WARNING, 핸들러 = 0개
  → logger.info(...) 는 전부 버려지고 있었다
```

실패(경고·예외)는 보이는데 **성공과 정황만 안 보이는** 상태였다. 즉 '조용한 실패를 읽을 수 있게 만들자'고 넣은 관측 장치가 정작 조용했다. 오늘 넣은 토큰 계량, 그리고 며칠 전에 넣은 '미인증 계정 N건 삭제'·'새 글 알림 N명 발송'도 전부 무음이었다.

### 4-6. 정적 분석 — 타입 검사를 처음 돌렸다

이 프로젝트에는 테스트가 300개 있고 린트도 돌고 있었다. 그런데 **타입 검사는 한 번도 안 돌렸다.** 오늘 처음 돌려서 결함 둘을 찾았다.

▶ 실제 출력 — mypy가 찾은 것 — 테스트 300개와 린트가 못 본 두 곳

```
① 데이터베이스 조회가 None을 돌려줄 수 있는데 바로 속성을 읽는다 → 500
   author = db.get(User, id)
   name = author.display_name        # author가 None이면 여기서 터진다
② 반환 타입이 (문자열, 문자열)인데 두 번째에 None이 들어갈 수 있었다
   def pick() -> tuple[str, str]:
       return model, model_provider(model)    # None을 돌려줄 수 있는 함수
```

왜 테스트가 못 봤을까. **테스트는 실행된 경로만 본다.** 위 두 곳은 '평소에는 안 일어나는 경우'라 테스트가 지나가지 않았다. 타입 검사는 실행하지 않고 **모든 경로의 가능성**을 본다. 그래서 겹치지 않는다.

> **🔎 비유** 테스트는 실제로 걸어본 길을 확인하는 것이고, 타입 검사는 지도를 펴서 '이 길로 가면 낭떠러지가 있다'를 보는 것이다. 둘 다 필요하고, 둘 중 하나로 다른 하나를 대신할 수 없다.

처음 돌렸을 때 경고가 19건 나왔다. 그걸 다 '무시'로 덮으면 검사를 켠 의미가 없어지므로, 실제 결함 둘은 고치고 나머지는 **왜 무시해도 되는지 근거를 파일에 적은 뒤** 0건으로 만들고 CI 게이트로 세웠다. 이제 새 코드에 같은 종류가 들어오면 빨간불이 뜬다.

> **🛠 전문가 노트** 검사를 새로 켤 때 제일 흔한 실패가 '경고가 너무 많아서 전부 무시로 처리하는 것'이다. 그러면 검사는 켜져 있는데 아무것도 안 막는다. 오늘의 주제인 '초록불의 두 종류'가 바로 그렇게 만들어진다. 0건으로 만든 다음에 켜는 게 순서다.

## 5. 밤 — 없앤 자동배포가 남긴 빈자리

2절에서 프론트 자동배포를 없앴다. 그런데 **없애면서 그 자리에 감지 장치를 안 넣었다.** 그래서 오늘 낮에 '개발일지 정적 아카이브가 아직 28편이 아니다'를 사람이 눈으로 발견했다.

이게 바로 오늘의 주제가 스스로 반복된 자리다. **자동을 끄면 '안 했다'가 조용해진다.**

그래서 배포할 때 산출물 안에 '어느 커밋으로 나갔는지'를 적어 두고, 감시가 그걸 읽어서 현재 커밋과 비교하게 했다.

▶ 실제 출력 — 감시에 붙인 절 — 실제로 여섯 갈래를 다 돌려서 확인했다

```
① 스탬프 없음      ⚠️  한 번도 배포 안 함 → Run workflow 안내
② 읽기 실패        ❌  권한/자격증명 문제 (‘배포 안 함’과 구분한다)
③ 형식 깨짐        ❌  배포 스크립트가 바뀌었는지 확인
④ 모르는 커밋      ⚠️  히스토리가 바뀌었거나 다른 브랜치
⑤ 최신             ✅  프론트 최신 (배포 b957827 · 그 뒤 변경 없음)
⑥ 뒤처짐           ⚠️  프론트가 19 커밋 뒤처져 있다 → 목록 출력
```

설계에서 두 번 고민한 게 있다.

**첫째, 파일 시각이 아니라 커밋 번호로 비교한다.** 파일 갱신 시각으로 비교하면, 내용이 같은 파일은 다시 업로드되지 않기 때문에 '테스트만 고친 날'에도 경고가 뜬다. 그리고 3절에서 배운 대로 **영원히 뜨는 경고는 없는 것과 같다.**

**둘째, 얕은 체크아웃이면 비교가 항상 통과한다.** 비교할 과거가 없으니까. 그래서 전체 이력을 받게 바꾸고, 혹시 얕으면 그 사실 자체를 경고로 말하게 했다. 오늘 하루 종일 본 병을 내가 또 심을 뻔한 자리였다.

같은 밤에 하나 더 고쳤다. 서버 보안 설정 값이 **비어 있으면** 우회 차단이 통째로 꺼지는데, 기존 검사는 '비ASCII 문자'만 봤고 빈 문자열은 그 검사를 그냥 통과했다. 비어 있으면 사이트는 멀쩡히 200이라 밖에서 아무 신호도 안 난다.

**⚠️ 함정**: 이 종류가 제일 무섭다. **반대 방향(값이 틀림)은 사이트가 통째로 죽어서 즉시 안다. 그런데 값이 비면 아무 일도 안 일어난다.** 시끄럽게 실패하는 쪽이 조용히 통과하는 쪽보다 언제나 낫다.

그리고 이 기동 검사 넷은 **테스트가 0건이었다.** 조용한 사고를 시끄럽게 만들려고 만든 장치가, 자기 자신은 조용히 사라질 수 있는 상태였다. 넷 다 테스트로 잠갔다.

## 6. 오늘 내가 저지른 것들

이 시리즈의 규칙 하나 — 내가 틀린 것도 적는다. 오늘은 특히 많았다.

- **실제 요금을 냈다.** 성능 테스트를 하면서 AI 초안 생성을 11번 실제로 호출했다. 로컬 설정 파일에 진짜 API 키가 들어 있는 걸 잊었다(입력 26,180 · 출력 2,044 토큰, 약 4센트). 금액은 작지만 원인이 나쁘다. 실수로 백 배를 부를 수도 있었다. 설정 템플릿에 빨간 경고를 적어 뒀다.
- **이미 올린 커밋을 고쳐서 꼬이게 만들었다.** 올린 다음인지 확인하지 않고 수정했다. 원격에 맞춰 되돌렸다.
- **에이전트 결과를 과장해서 전했다.** '다섯 건 다 사실'이라고 했는데 반박에서 둘이 깎였다. 바로 정정했다.
- **있지도 않은 문제를 보고했다.** 글 두 편에 취소선이 그어져 있다고 했는데, 실제로는 코드 블록 표시였다. 그 오판 때문에 라이브러리를 하나 추가할 뻔했다(gzip 11KB). 다시 재보고 안 넣었다.
- **내가 만든 검사가 코드 블록 안을 검사했다.** 정확히 이 저장소가 반복해서 잡아온 '주석 안의 문자열까지 세는' 병이다. 코드 블록을 걷어내고 다시 증명했다.

린트가 나를 두 번 잡았고 두 번 다 린트가 옳았다. 그때마다 더 나은 코드가 나왔다.

> **🛠 전문가 노트** **틀린 것을 적는 게 겸손해 보이려는 장치는 아니다.** 이 목록이 다음에 같은 자리에서 멈추게 한다. '로컬에 진짜 키가 있다'는 한 줄이, 다음에 성능 테스트를 할 사람에게 제일 값진 문장일 것이다.

## 7. 마지막으로, 틀린 예측 하나를 재서 지웠다

'상태 기록 표가 커지면 상태 페이지가 8배 느려진다'는 예측이 후보 목록에 남아 있었다. 논쟁 대신 쟀다. 180일치(약 26만 행, 29MB)를 실제로 심고 재봤다.

▶ 실제 출력 — 실측 — 예측이 틀렸다

```
days=30  →  21 ms   (인덱스 범위 스캔, 43,213행만 읽음)
days=90  →  51 ms   (요청 상한이 90일이므로 이게 최악이다)
표 전체  →  68 ms   (상한 때문에 이 경로는 도달 불가)
```

읽는 양이 **표 크기가 아니라 조회 기간**에 묶여 있었다. 그래서 오래된 기록을 지우는 정책은 성능 때문에 필요한 게 아니다. 1년이면 약 59MB고, 지우면 과거 가동률 기록만 사라진다.

숫자를 코드 옆에 적어 뒀다. **다음에 누가(혹은 내가) 같은 걱정을 다시 꺼내면 그 자리에서 끝나게 하려고.**

## 8. 오늘 배운 것

초록불에는 두 가지가 있다. **'봤는데 괜찮았다'와 '안 봤다'.** 화면에서는 똑같이 생겼다. 오늘 나온 것들을 늘어놓으면 전부 두 번째였다.

- 감시 280회 초록 — 원본이 0개라 '확인할 것 없음'으로 넘어갔다
- 배포 게이트 통과 — 이번 푸시의 변경분만 봤다
- 문법 검사 통과 — 폴더 한 겹을 안 봤다
- 테스트 300개 통과 — 실행되지 않은 경로는 못 본다
- 로그 정상 — 사실은 한 줄도 안 나가고 있었다
- 기동 검사 넷 — 테스트가 0건이라, 사라져도 아무도 모른다

공통점이 있다. **전부 '검사가 실패하지 않았다'는 사실을 '검사가 통과했다'로 읽은 것**이다. 그 둘은 다르다. 실패는 신호를 내지만 침묵은 통과처럼 보인다.

그래서 오늘 고친 것들은 대부분 기능이 아니라 **'못 본 것을 못 봤다고 말하게 만드는 일'**이었다. 읽기 실패와 '없음'을 구분하고, 얕은 이력에서는 비교했다고 하지 않고, 0건일 때 조용히 넘어가지 않고.

곁들임: "영원히 빨간불인 검사는 없는 검사와 같다. 그래서 오탐을 줄이는 일은 편의가 아니라 **감시가 살아 있게 하는 일**이다."
