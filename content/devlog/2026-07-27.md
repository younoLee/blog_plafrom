# 블로그 만들기 #20 — 재보지 않으면 모르는 것들 (DR 게임데이 · IR 훈련)

> 입문자가 읽어도 이해되게 — '백업이 있다'와 '복구된다'가 왜 다른 말인지, '열쇠를 껐다'와 '잠겼다' 사이에 왜 시간 차가 있는지, 그리고 감시 장치가 어떻게 '초록불인데 아무것도 안 보고 있는' 상태가 되는지 위주로.

이번 편의 형식: 지난 편은 AWS 화면 캡처를 실었는데, 오늘의 증거는 그림이 아니라 명령이 뱉은 문자열이었다. 그래서 터미널 출력을 그대로 넣었다. 회색 고정폭 글씨가 전부 실제로 화면에 찍힌 것이다.

## 0. 오늘 한 일 한눈에

이 프로젝트에는 '안전장치'가 여럿 있다. 백업, 복구 문서, 감시 스크립트, 권한 설정 같은 것들이다. 문제는 이런 게 전부 **평소엔 아무 일도 안 한다**는 점이다. 진짜로 필요한 순간에 처음 쓰이는데, 그때 안 되면 이미 늦는다.

그래서 오늘은 일부러 사고를 냈다. 두 번.

- 오전 — 재해 복구 훈련(DR 게임데이): 운영 서버를 진짜로 삭제하고, 복구 문서만 보고 되살렸다.
- 오후 — 보안 사고 훈련(IR): '내 노트북이 털렸다'고 가정하고 자격증명을 실제로 전부 갈아끼웠다.
- 저녁 — 심층검사: 그 훈련들이 만들어낸 코드를 스스로 공격해서 버그 두 개를 찾아 고쳤다.
- 마지막 — 훈련이 찾아낸 약점을 실제로 막았다(백업을 관리자 권한으로도 못 지우게).

> **🔎 비유** 소화기를 벽에 걸어두는 것과, 불을 붙여놓고 실제로 꺼보는 것의 차이다. 오늘은 후자를 했다. 그리고 예상대로 소화기 몇 개가 고장나 있었다.

## 1. 아침 — 어제 못 끝낸 테스트부터

어제 컴퓨터의 도커가 죽어서 백엔드 테스트만 못 돌리고 멈춰 있었다. 도커가 살아나서 이어 돌렸다.

여기엔 사연이 있다. 이 컴퓨터의 파이썬은 사실상 망가져 있다 — 패키지를 설치하는 도구(pip)도, 격리 환경을 만드는 도구(venv)도 없고, 관리자 권한도 못 쓴다. 그래서 백엔드 테스트를 **로컬에서 돌릴 방법이 아예 없다**. 대신 자동 검사 서버(CI)와 똑같은 환경을 컨테이너로 만들어서 그 안에서 돌린다.

▶ 실제 출력 — 컨테이너 안에서 돌린 백엔드 테스트

123 passed, 190 warnings in 33.48s

Required test coverage of 70% reached. Total coverage: 78.23%

> **🛠 전문가 노트** 이 방식은 지난주에 데인 경험에서 나왔다. 그때는 로컬에서 117개가 전부 통과하는데 CI에서만 3개가 실패했다. 원인은 내 컴퓨터엔 메일 서버가 떠 있고 CI엔 없다는 차이였다. '로컬에서 되는데요'는 증거가 아니다 — 같은 환경을 만들어 재현해야 원인이 보인다.

## 2. 재해 복구 훈련 — 서버를 진짜로 지웠다

### 2-1. 왜 '진짜로' 지워야 했나

이 프로젝트엔 이미 복구 문서가 있다. 지난주에 한 번 연습도 했다. 그런데 그 연습은 **임시 서버를 새로 띄워서** 한 것이라, 운영 서버는 손대지 않았다. 그건 '백업이 복원된다'까지만 증명한다. '서비스가 돌아온다'는 다른 명제다.

> **🔎 비유** 비상구가 어디 있는지 아는 것과, 불이 났을 때 그 문이 실제로 열리는지는 다른 얘기다. 문이 페인트로 붙어 있을 수도 있다.

### 2-2. 지우기 전에 안전한지부터 쟀다

무모하게 지운 게 아니다. 훈련은 '안전하니까 한다'가 아니라 **안전한지 먼저 재고 한다**. 착수 전에 확인한 것들:

- 서버는 지난주에 끈 뒤로 한 번도 켜지지 않았다 — 그러니 데이터가 바뀌었을 리 없다.
- 마지막 백업이 서버를 끄기 정확히 35초 전에 떠 있었다 — 즉 백업 = 현재 상태. 잃을 게 0이다.
- 사이트는 이미 백엔드가 꺼진 상태라 사용자 영향도 0이다.
- 그럼에도 디스크 스냅샷을 '깨진 유리' 용도로 하나 떠 뒀다. 쓰지 않기로 하고 시작했고, 실제로 쓰지 않았다.

그리고 지웠다. 서버의 디스크에는 데이터베이스가 통째로 들어 있었고, 서버를 삭제하면 디스크도 같이 사라지는 설정이었다.

▶ 실제 출력 — 삭제 후 디스크를 조회해봤다

An error occurred (InvalidVolume.NotFound) when calling the DescribeVolumes

operation: The volume 'vol-01f2ebe825fe7d725' does not exist.

재해가 성립했다. 여기서부터 시계를 켰다.

### 2-3. 첫 명령부터 실패했다

복구 문서의 1번 명령은 '서버를 다시 만들어라'는 한 줄이다. 그걸 그대로 쳤더니:

▶ 실제 출력 — 복구 문서 1단계를 그대로 실행

Error: No value for required variable

on ecs.tf line 9:

9: variable "backend_image_tag" {

사흘 전에 다른 작업을 하면서 설정 파일에 '반드시 값을 채워야 하는 항목'을 하나 추가했는데, 그게 복구 경로까지 막아버린 것이다. 그 작업 이후로 아무도 복구 문서를 다시 밟아보지 않았다.

**⚠️ 함정** — 재해 한복판에서 첫 삽이 안 들어간다. 이게 훈련하지 않으면 절대 안 보이는 종류의 고장이다. 문서는 그대로인데, 문서가 가리키는 세상이 바뀐 것이다.

억지로 값을 채워 넘겼더니 이번엔 더 나쁜 게 나왔다. 지난주에 일부러 정리해서 없앤 고가 인프라(월 $50~70짜리)가 통째로 되살아나려 했다.

▶ 실제 출력 — 우회한 뒤 무엇이 만들어지는지 미리 본 결과

# aws_db_instance.main will be created

# aws_ecs_service.backend will be created

# aws_lb.backend will be created

... (외 7개)

Plan: 10 to add, 0 to change, 0 to destroy.

> **🛠 전문가 노트** 재해 복구 중에 쓰지도 않을 인프라가 살아나면 돈만 나가는 게 아니라, 그것들이 뜨기를 기다리느라 복구가 더 늦어진다. 급할 때일수록 '건드리는 범위'를 좁혀야 한다.

### 2-4. 42분 중 20분을 잡아먹은 공백 한 칸

서버는 13초 만에 다시 만들어졌다. 문제는 그 다음이었다. 새로 만든 서버를 찾는 명령이 **아무것도 못 찾았다.**

원인은 어이없게도 이름표에 붙은 **공백 한 칸**이었다. 서버 이름표가 'blog-backend '(뒤에 공백)로 돼 있었는데, 조회 명령이 그 공백을 조용히 잘라내버려서 영원히 일치하지 않았다.

▶ 실제 출력 — 같은 서버를 세 가지 방법으로 찾아본 결과

런북 원문(공백 포함): None

공백 없음         : None

JSON 형식 필터     : i-0abdd1afc7041e167

셋째 방법으로만 찾힌다. 그런데 사고 한복판에서 '아 이건 공백 때문이니 JSON 형식으로 바꿔야지'라는 생각이 들 이유가 없다. 결과는 빈 값이 다음 명령으로 흘러가서 엉뚱한 에러로 죽는 것이다.

**걸린 시간** — 약 20분. 전체 복구 시간 42분의 절반에 가깝다.

나머지 단계는 오히려 싱거웠다. 서버 기본 설치 57초, 코드 올리기 1초, 비밀값 복원 1초, 데이터베이스 기동 21초, 백업 복원 3초.

### 2-5. '어차피 안 할 것'이라던 작업이 실제로 돌았다

복구 문서에는 '이 단계에서 데이터베이스 구조 변경은 이미 최신이라 아무 일도 안 일어난다'고 단언하는 주석이 있었다. 실제로는 이렇게 나왔다.

▶ 실제 출력 — 백엔드가 뜨면서 남긴 로그

INFO  [alembic.runtime.migration] Running upgrade b7f1c4e29a03 -> c1d2e3f4a5b6,

add index on posts.created_at (정렬 핫패스)

백업은 지난주 것이고 코드는 그 뒤로 바뀌었으니 당연히 차이가 있었던 것이다. 이번엔 색인 하나라 무해했지만, 백업이 오래될수록 여기서 진짜 작업이 돌고, 실패하면 백엔드가 아예 안 뜬다.

**⚠️ 함정** — 문서에 '안 일어난다'고 써 있으면, 정작 그게 일어나서 실패했을 때 원인을 그 자리에서 찾지 않게 된다. 단언은 편하지만 위험하다.

### 2-6. 결과

▶ 실제 출력 — 복구 완료 시점의 서비스 상태

{"backend":"ok","database":"ok","mail":"ok",

"stats":{"posts":27,"subscribers":4}}

복원된 데이터: posts=27, users=5, comments=4, payments=2

**RTO(복구 소요)** — 42분 08초 — 복구 착수부터 서비스가 공개 주소에서 응답하기까지

**데이터 손실** — 0 — 글·유저·댓글·결제 전부 복원

**찾은 문서 결함** — 5건 (전부 그날 수정)

> **🛠 전문가 노트** 오늘 가장 값진 숫자는 42분이 아니라 그 안의 분포다. **실제 재건 작업의 합은 5분이 안 된다.** 나머지는 문서가 틀린 자리에서 헤맨 시간이다. 재해 복구 시간은 작업량이 아니라 문서의 정확도가 지배한다.

## 3. 보안 사고 훈련 — 열쇠를 전부 갈아끼웠다

### 3-1. 시나리오: 이 노트북이 털렸다

이 컴퓨터 한 대에 세 가지가 같이 산다. AWS 계정 전체를 다룰 수 있는 열쇠, 서버의 비밀값 사본, 그리고 서버에 접속하는 개인키다. 하나가 아니라 셋이 동시에 나가는 구조다.

> **🔎 비유** 집 열쇠, 금고 비밀번호, 그리고 예비 열쇠 보관함 열쇠를 전부 같은 가방에 넣고 다니는 셈이다. 가방을 잃으면 하나가 아니라 전부를 잃는다.

### 3-2. 좋은 소식 — 최소권한이 실제로 값을 했다

서버가 통째로 털렸다고 가정했을 때 백업까지 같이 잃는지 확인했다. AWS에는 '이 권한으로 이걸 할 수 있나'를 실제로 물어보는 기능이 있다.

▶ 실제 출력 — 서버의 권한으로 백업 저장소에 무엇을 할 수 있나

s3:PutObject     (자기 백업 올리기)      allowed

s3:GetObject     (백업 읽기)             implicitDeny

s3:DeleteObject  (백업 지우기)           implicitDeny

s3:PutObject     (마지막 보루 덮어쓰기)  implicitDeny

s3:ListBucket    (목록 보기)             implicitDeny

서버는 백업을 **올릴 수만 있고 읽지도 지우지도 못한다.** 서버가 털려도 백업은 유출되지 않고, 서버를 장악한 공격자가 백업을 인질로 잡을 수도 없다.

> **🛠 전문가 노트** '최소권한'은 자주 하는 말이지만 실제로 값을 하는 순간이 이런 때다. 필요한 것 하나(올리기)만 주면, 침해 범위가 그 하나로 갇힌다.

### 3-3. 나쁜 소식 — 기록은 남는데 보는 눈이 없었다

AWS에는 '누가 무엇을 했나'를 전부 기록하는 장치가 켜져 있었다. 실제로 오늘 아침 내가 서버를 다시 만든 것도 기록에 남아 있었다.

문제는 그걸 **아무도 보고 있지 않았다**는 것이다. 이상 징후를 실시간으로 알려주는 장치가 하나도 없었다. 유일한 자동 탐지가 '이번 달 요금이 $10을 넘으면 알림'이었다.

**⚠️ 함정** — 기록(로그)과 탐지(알림)는 다르다. 기록은 사고가 난 뒤에 되짚을 때 쓰고, 탐지는 사고를 알아차릴 때 쓴다. 기록만 있으면 '알아차리기'는 여전히 운에 맡기는 것이다.

사각지대도 하나 찾았다. 메일 발송용 열쇠는 아무리 도난당해 스팸을 뿌려도 그 기록 장치에 **흔적이 전혀 남지 않는다**. 기록 대상이 아니기 때문이다.

### 3-4. '껐다'와 '막혔다' 사이에는 시간이 있다

열쇠를 갈아끼우는 건 새 열쇠를 만들고 옛 열쇠를 버리는 일이다. 그런데 옛 열쇠를 '사용 중지'로 바꾼 직후에 그 열쇠로 로그인을 시도해봤더니 — 성공했다.

▶ 실제 출력 — 옛 열쇠를 사용 중지한 뒤 반복해서 찔러본 결과

사용 중지 처리

+12초  아직 인증됨

+40초  ✅ 거부됨 — SMTPAuthenticationError

(관리자 열쇠도 같았다)

+ 0초  아직 살아 있다

+11초  ✅ 거부됨 — InvalidClientTokenId

수십 초의 창이 있다. 사고가 진행 중일 때 '열쇠 껐으니 됐다'고 안심하면 안 된다는 뜻이다.

> **🔎 비유** 현관 비밀번호를 바꿔도, 이미 안에 들어와 있는 사람은 바로 안 나가는 것과 비슷하다. 잠그는 것과 쫓아내는 것은 다른 일이다.

### 3-5. 갈아끼운 뒤에는 반드시 '옛 것이 죽었는지'를 본다

갈아끼우기의 진짜 검증은 '새 것이 된다'가 아니라 **'옛 것이 안 된다'**이다. 세 가지를 각각 확인했다.

특히 세션 열쇠는 교체하면 기존 로그인이 전부 무효가 돼야 한다. 옛 열쇠로 만든 출입증과 새 열쇠로 만든 출입증을 같은 문에 대봤다.

▶ 실제 출력 — 옛 열쇠로 만든 출입증 vs 새 열쇠로 만든 출입증

옛 SECRET_KEY로 서명한 토큰  →  HTTP 401

새 SECRET_KEY로 서명한 토큰  →  HTTP 200

의도대로다. 옛 것은 거부되고 새 것만 통한다.

> **🛠 전문가 노트** '지웠다'는 증거가 아니다. 지운 것으로 실제로 문을 열어보고 안 열려야 증거다. 이 프로젝트가 반복해서 배우는 문장의 또 다른 판본이다.

## 4. 심층검사 — 내가 만든 버그 두 개

훈련의 산출물로 감시 스크립트에 검사 항목을 새로 넣었다. '기록 장치가 살아 있는가', '열쇠 개수가 늘지 않았는가' 같은 것들이다. 그리고 그 코드를 스스로 검사했다.

### 4-1. 내가 쓴 경고를 내가 어겼다

그 코드에 나는 이런 주석을 달아뒀다 — '항상 빨간불인 경보는 아무도 안 보는 경보와 같으니, 오탐이 구조적으로 불가능한 것만 검사한다.' 그리고 정확히 그 반대를 만들었다.

감시 스크립트는 매시간 자동으로 도는데, 그때는 내 컴퓨터가 아니라 **권한이 훨씬 좁은 자동화 계정**으로 돈다. 그 계정에는 내가 새로 추가한 검사에 필요한 권한이 없었다.

▶ 실제 출력 — 자동화 계정이 새 검사를 할 수 있는지 물어본 결과

cloudtrail:GetTrailStatus   implicitDeny

iam:ListAccessKeys          implicitDeny

즉 매시간 3건씩 실패하면서 실패 메일을 보내는 상태였다. 내 컴퓨터에서는 관리자 권한이라 멀쩡히 통과했기 때문에 보이지 않았다.

**⚠️ 함정** — 오늘 아침에 배운 것과 똑같은 병이다 — '로컬에서 되는데요'. 하루에 같은 함정을 두 번 밟았다.

필요한 권한 두 개를 **대상까지 좁혀서** 추가했다. 감시용 계정에 계정 전체 열람 권한을 주는 건 그 자체로 위험을 늘리는 일이라서다.

### 4-2. 가짜 초록

두 번째 버그가 더 고약하다. 열쇠의 나이를 계산하는 코드였는데, 나이 정보를 **못 읽었을 때** 빈 값이 계산에 들어가면서 '0일'로 처리됐다.

▶ 실제 출력 — 정보를 못 읽는 상황을 재현해봤다

age=[0]

✅ OK 경로 (나이 [0]일로 출력됨)

눈이 먼 상태가 '✅ 정상, 열쇠 1개, 0일'이라는 초록불로 보고된다. 감시가 고장났는데 감시는 문제없다고 말하는 상태다.

> **🔎 비유** 화재경보기 배터리가 빠졌는데 표시등은 초록불인 것과 같다. 빨간불보다 위험하다 — 빨간불은 최소한 쳐다보게라도 만든다.

> **🛠 전문가 노트** 이 프로젝트는 정확히 이 형태로 4주를 잃은 적이 있다. 메일이 한 통도 안 나가는데 상태 페이지가 25,826번 '메일 정상'이라고 답했다. 그래서 '못 읽었다'는 항상 실패로 취급한다는 규칙이 있는데, 새로 쓴 코드에서 그 규칙을 빠뜨렸다.

## 5. 찾은 약점을 실제로 막았다

훈련이 찾아낸 것 중 가장 무거운 게 하나 남아 있었다. 서버가 털려도 백업은 안전하지만, **관리자 열쇠가 털리면 백업을 영구히 지울 수 있다**는 점이다.

이걸 문서에 '남은 위험'으로 적어둘지, 실제로 막을지 고민하다가 막기로 했다. 저장소가 공개라 약점 목록을 적어두는 게 오히려 지도를 그려주는 셈이기도 했다.

S3에는 '한 번 올리면 정해진 기간 동안 아무도 못 지우게' 하는 잠금 기능이 있다. 두 가지 모드가 있는데 이 선택이 핵심이었다.

- 느슨한 모드 — 관리자 권한으로 우회할 수 있다. 우리 위협이 바로 '관리자 열쇠 유출'이라 무의미하다.
- 엄격한 모드 — 최고 관리자를 포함해 아무도 기간 내에는 못 지운다. 이걸 골랐다(14일).

그리고 정말 막히는지 관리자 권한으로 직접 삭제를 시도했다. 우회 옵션까지 붙여서.

▶ 실제 출력 — 관리자 자격증명으로 백업 삭제를 시도한 결과

$ aws s3api delete-object --key keep/latest.sql.gz --version-id ...

AccessDenied ... object protected by object lock

$ ... --bypass-governance-retention        (우회 옵션까지)

AccessDenied ... object protected by object lock

같은 방법으로 감사 기록 저장소도 잠갔다. 침해자가 자기 흔적을 지우는 걸 막기 위해서다.

### 5-1. 켜기 전에 부작용 셋을 먼저 쟀다

이런 변경은 조용히 뭔가를 부수기 쉽다. 특히 '백업이 안 올라가는' 부작용이 생기면 치명적인데 한참 뒤에나 알아차린다. 그래서 하나씩 확인했다.

- 설정 도구가 저장소를 통째로 갈아엎으려 드는가 → 덜 중요한 저장소에서 먼저 시험하고 확인 후 진행.
- 백업 올리기가 깨지는가 → 서버와 똑같은 권한을 가진 임시 신분을 만들어 실제로 올려봤다. 성공.
- 이미 있던 파일에도 적용되는가 → **안 된다.** 켠 직후 가장 중요한 파일이 여전히 삭제 가능했다.

**⚠️ 함정** — 셋째가 특히 위험했다. '잠갔다'고 생각하고 넘어갔으면 정작 제일 중요한 백업만 안 잠긴 채로 남을 뻔했다. 기존 18개 파일에 잠금을 직접 걸어줬다.

**비용** — 사실상 0원. 잠금 기능 자체는 무료고, 두 저장소를 합쳐 9MB라 월 1센트 미만이다.

**대가** — 돈이 아니라 유연성이다. 잘못 올린 것도 14일간 못 지운다.

## 6. 오늘의 교훈

오늘 하루를 관통한 문장은 하나다 — **'써놓은 것'과 '되는 것'은 다르다.**

- 복구 문서는 3일 전 작업 때문에 첫 명령부터 깨져 있었다. 밟아보지 않으면 몰랐다.
- '아무 일도 안 일어난다'는 주석은 틀렸다. 실제로는 일이 일어났다.
- 열쇠를 껐다고 바로 막히지 않았다. 수십 초가 걸렸다.
- 내가 만든 감시 코드는 자동 실행 환경에서 전부 실패했다. 내 컴퓨터에서만 초록이었다.
- 잠금을 켰지만 기존 파일에는 적용되지 않았다. 확인하지 않았으면 몰랐다.

다섯 개 전부 '설정은 맞았는데 동작은 달랐던' 경우다. 그리고 다섯 개 전부 **재봤기 때문에** 발견됐다.

> **🔎 비유** 건강검진과 비슷하다. 아프지 않다고 건강한 게 아니라, 재봐야 아는 것이 있다. 오늘은 재보고 다섯 군데를 고쳤다.
