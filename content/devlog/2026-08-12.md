# 블로그 만들기 #30 — 내가 만든 검사가 나를 안심시켰다

> 입문자가 읽어도 이해되게 — '검사를 만들었다'와 '그 검사가 실제로 돌고 있다' 사이의 거리, 그리고 고치겠다는 제안을 먼저 반박해보는 일이 왜 값을 하는지 위주로.

이번 편의 형식: 앞 편들처럼 실제 터미널 출력을 그대로 실었다. 회색 고정폭 글씨는 전부 오늘 화면에 찍힌 문자열이다. 내 판단이 틀린 자리도 틀린 채로 남겼다.

## 1. 아침 — 밀린 것부터 닫았다

어제까지 배포되지 않은 커밋이 8개 쌓여 있었다. 서버를 켜고, 코드를 올리고, 재빌드하고, 개발일지 #29를 발행했다. 여기까지는 평범한 마무리 작업이다.

다만 한 가지는 습관대로 하지 않았다. 목록에 '미배포 8커밋'이라고 적혀 있어도 그 목록을 믿지 않고, **운영 서버 안의 코드 해시를 직접 떠서 로컬과 비교**했다.

▶ 실제 출력 — 배포 전후 해시 비교

```
로컬 app/**.py:        57015d26d2c3
운영 컨테이너(배포 전): 82719ff32115   ← 다르다. 미배포가 맞다
운영 컨테이너(배포 후): 57015d26d2c3   ← 일치
```

이 습관은 어제 얻은 것이다. 어제는 '미배포'라고 적힌 목록이 틀렸었다(이미 배포돼 있었다). 오늘은 목록이 맞았다. **중요한 건 맞았다는 게 아니라, 맞는지 재봤다는 쪽이다.**

### 그리고 목록이 또 썩어 있었다

메모에 '남은 PR 5개'가 적혀 있었다. 손대기 전에 원격을 조회했더니 dependabot 브랜치가 **하나만** 남아 있었다. 다섯 건은 내용이 이미 main에 들어가 있었고 PR은 그래서 닫혔다.

▶ 실제 출력 — 실제 확인 — 기록 vs 실제

```
#21 terraform aws 6.55→6.57  →  락파일이 이미 6.58.0
#16 setup-terraform 4.0.1     →  이미 SHA 핀
#15 setup-python 7.0.0        →  이미 SHA 핀
#23 react 19.2.8              →  이미 ^19.2.8
#17 @types/node 26            →  이미 ^26.1.2
```

> **🛠 전문가 노트** 이 저장소에서 '안 한 일 목록'이 썩은 게 다섯 번째다. 교훈은 매번 같다 — **목록은 사본이고 진실은 다른 곳에 있다.** PR의 진실은 GitHub이고, 배포의 진실은 서버 안의 해시다.

## 2. "다른 블로그 보면 내 게 초라하지 않아?"

밀린 일을 닫고 나서 받은 질문이다. 답하려면 재봐야 했다. 그래서 네 갈래로 나눠 조사했다 — 저장소 안의 기능 목록, 외부 블로그들의 표준선, 라이브 사이트 실측, 첫인상 진단.

결과가 예상과 달랐다.

**기능이 부족한 게 아니었다.** 검색·태그·페이지네이션·목차·시리즈 네비·읽는 시간·다크모드·댓글·RSS·sitemap·구독·웹푸시·상태 페이지가 이미 다 있었다. 표준선에서 빠진 건 코드 하이라이팅·공유 버튼·관련 글 정도였다.

진짜 문제는 다른 데 있었다.

▶ 실제 출력 — 실측 — 첫 화면이 보여주는 것

```
랜딩(/)의 구성:      입구 카드 2장
글 제목:             0개
날짜·발췌:           0개
가진 콘텐츠:         개발일지 29편 · 237,993자
첫 화면 노출:        0%
```

게다가 글 목록은 전부 서버에서 온다. 그런데 이 사이트는 **비용 때문에 서버를 평소 꺼둔다.** 즉 방문자가 가장 흔하게 보는 상태가 **빈 화면**이었다. 서버 없이 읽히는 유일한 경로(정적 개발일지 아카이브)는 **푸터의 12px 회색 글씨**였다.

> **🔎 비유** 가게로 치면, 창고에 물건이 24만 개 있는데 쇼윈도에는 '들어오세요' 안내판 두 개만 걸어둔 셈이다. 게다가 문은 평소 잠겨 있고, 열려 있는 옆문 표시는 발밑에 손톱만하게 붙어 있다.

### 채용하는 쪽이 보는 것도 같이 조사했다

설문 자료(채용 담당자·리드 60명+)에서 나온 결론은 '개인 사이트는 보긴 하지만 없다고 불리하진 않다'였다. 값이 매겨지는 건 **코드 구조**, **기술적 판단의 서술**, 그리고 **블로그 글 자체**였다. 반대로 직접 감점되는 건 두 가지 — 나쁜 디자인, 그리고 낡은 정보 방치.

> **🛠 전문가 노트** 조사를 맡긴 쪽이 스스로 인용을 걸러낸 것도 적어둔다. '채용 담당자 73%가 포트폴리오를 중시' 같은 통계가 검색에 많이 나오는데 **1차 출처 추적에 실패해 쓰지 말라**고 표시해 왔다. 숫자가 그럴듯하다고 쓰면, 나중에 그 숫자를 근거로 내린 결정이 통째로 흔들린다.

## 3. 그래서 고친 것 — 기능이 아니라 노출

첫 화면이 서버 없이 글 목록을 그리게 했다. 방법은 새 API가 아니라 **빌드 시점**이다. 정적 아카이브를 만드는 스크립트가 이미 원고를 읽고 있으니, 거기서 목록 파일 하나를 더 뱉게 했다.

링크도 앱 라우트가 아니라 정적 아카이브로 걸었다. **서버가 꺼져 있어도 클릭이 살아 있어야** 목록을 그린 의미가 있기 때문이다.

▶ 실제 출력 — 배포 후 실측 — 서버가 꺼진 상태에서

```
/api/status          → 타임아웃 (서버 정지, 의도된 상태)
/devlog-index.json   → 200 · 29편 · 237,993자
첫 화면 링크 29개    → 전수 200, 비-200 0건
```

같이 붙인 것 넷: 공유 버튼, 코드 복사 버튼, 404 화면, 그리고 공유 카드 이미지.

공유 버튼은 조금 특이하게 만들었다. 앱의 글 주소를 공유하면 **어느 글이든 미리보기 카드가 똑같이** 뜬다(봇은 자바스크립트를 실행하지 않으므로 빈 껍데기를 본다). 그래서 같은 글의 정적 아카이브 주소가 있으면 그쪽을 복사한다 — 편마다 제 제목이 붙어 있고, 서버가 꺼져 있어도 열린다.

공유 카드 이미지는 원래 343×361이었다. 큰 카드 기준(1200×630)에 한참 못 미쳤다. 이 환경엔 이미지 라이브러리도 폰트 파일도 없어서, 표준 라이브러리만으로 PNG를 직접 써서 만들었다 — 이 저장소가 앱 아이콘을 만들 때 쓴 방식 그대로다.

**한계** — 한글은 폰트 없이 그릴 수 없어 'DEV'와 번개만 넣었다. 제목·설명은 어차피 카드에 따로 뜬다.

## 4. 저녁 — 오늘 쓴 코드를 검사했다

여덟 갈래로 나눠 붙였다: 정확성 · 보안 · 회귀 · 테스트 품질 · 병목 · 장애 · 동적 분석 · 완전성 비평. 그리고 결과를 바로 받아들이지 않고 **서로 반박시켰다.**

첫 번째로 나온 게 가장 아팠다.

### 감시를 넣은 커밋이 감시를 죽였다

어제 나는 '프론트가 배포됐는지 아무도 안 보고 있다'는 걸 발견하고 감시에 한 절을 추가했다. 오늘 그 감시가 **19시간째 죽어 있었다**는 걸 알았다.

▶ 실제 출력 — 실제 이력 — 감시 워크플로

```
2026-08-11T11:04:53Z  success
2026-08-11T11:18Z     ← 내가 감시를 추가한 커밋을 푸시
2026-08-11T11:56:16Z  failure
2026-08-11T13:42:24Z  failure
...                   (14회 연속)
2026-08-12T08:39:15Z  failure
```

원인은 권한 한 줄이었다. 새로 넣은 검사는 S3의 파일 하나를 읽는데, 감시가 쓰는 계정에는 그 버킷의 **목록 권한만** 있고 읽기 권한이 없었다. 감시 코드를 고치면서 **권한 파일은 안 건드렸다.**

▶ 실제 출력 — 권한 확인

```
s3:GetObject on blogplafromops/deploy-stamp.txt  →  implicitDeny
```

그런데 진짜 문제는 원인이 아니라 **내가 왜 몰랐는가**다.

**⚠️ 함정** — 나는 그 감시 스크립트를 **내 노트북에서** 돌려서 '이상 없음'을 확인했고, 그걸 보고했다. 내 계정에는 그 권한이 있다. 그래서 **로컬은 초록, 클라우드는 빨강**이었다. 이 저장소가 이미 여덟 번 겪은 '로컬만 초록'을 내가 그대로 밟았다.

> **🔎 비유** 화재경보기를 새로 달고, 내 방에서 리모컨으로 테스트해 '잘 울린다'고 적어둔 것과 같다. 정작 경보기는 전원이 안 연결돼 있었고, 19시간 동안 아무 소리도 못 냈다.

### 내가 어제 만든 게이트는 실패할 수 없는 게이트였다

어제 나는 '첫 화면 목록이 가리키는 링크가 실제로 있는지'를 배포에서 검사하게 만들고, 일부러 깨뜨려서 빨간불이 뜨는 것까지 확인했다. 오늘 검사가 그 확인이 헛것이라고 했다.

내가 깨뜨린 건 **손으로 고친 파일**이었다. 실제 배포에서는 그 목록과 링크가 **같은 프로그램의 같은 배열 세 줄 위에서** 만들어진다. 즉 서로 어긋날 수가 없다. 24가지 상황을 넣어보니 **17개가 그대로 통과**했다 — 같은 글이 29번 중복돼도, 제목이 파일과 전혀 무관해도, 순서가 뒤집혀도.

> **🛠 전문가 노트** '검사인 척하는 검사'는 없느니만 못하다. 없으면 불안하기라도 한데, 있으면 안심시킨다.

### 내 테스트는 결함의 절반을 통과시켰다

테스트 품질을 본 갈래는 내 코드에 결함을 하나씩 심어보고 테스트가 잡는지 셌다.

▶ 실제 출력 — 결과

```
심은 결함 59개 중 살아남은 것: 31개 (53%)
살아남은 예:
  · 첫 화면 애니메이션을 '영원히 안 보이게' 바꿔도 통과
  · 목록을 5개→3개로 줄여도 통과 (내 픽스처가 2편뿐이라)
  · 목록 순서를 뒤집어도 통과
  · 복사할 값을 빈 문자열로 바꿔도 통과
```

정리하면 내 테스트가 잠근 건 **'무엇을 부르는가 / 어디로 링크하는가 / 어떤 값을 넘기는가'**였고, 못 잠근 건 **'실제로 복사되는가 / 실제로 보이는가 / 목록이 파일과 맞는가'**였다. 셋 다 검사가 자기가 만든 값이나 형태만 보고 있었다.

## 5. 고치겠다는 제안을 먼저 반박시켰다 — 두 번 다 막혔다

지적을 받으면 바로 고치고 싶어진다. 오늘은 그러지 않고, 내 수정안을 다시 공격하게 했다. 두 번 다 그 절차가 사고를 막았다.

### ① 한 줄 옮기려다 전 사용자를 깰 뻔했다

복사 버튼의 임시 요소가 실패 시 화면에 남는다는 지적이 있었다. 나는 '정리 코드를 finally로 옮기면 된다'고 했다. 반박은 이랬다 — 그 변수는 **한쪽 분기 안에서만 선언**돼 있어서, finally로 옮기면 **다른 쪽 분기에서 없는 변수를 지우려다 터진다.** 그리고 이 사이트는 항상 그 다른 쪽으로 간다.

게다가 원래 지적 자체가 반쯤 틀렸다. 그 복사 명령은 **실패해도 예외를 던지지 않고 false를 돌려준다.** 진짜 결함은 다른 데 있었다 — 반환값을 안 보고 있어서 **아무것도 복사 안 됐는데 '복사됨'이라고 말하고 있었다.**

더 뼈아픈 건 내가 그걸 잠갔다고 믿었다는 것이다. '실패하면 복사됨이라고 하지 않는다'는 테스트를 분명히 썼는데, 그 테스트는 **성공만 고정한 가짜**를 통과시키고 있었다.

### ② 보안을 강화하려다 사이트 전체 인증을 죽일 뻔했다

로그인 토큰 검증에 '이 항목들은 반드시 있어야 한다'는 옵션을 넣으려 했다. 상식적인 강화다.

반박이 실제로 토큰을 만들어 넣어봤다. 로그인 토큰에는 '용도' 항목이 **없다.** 그런데 검증 코드는 용도 항목이 **있으면** 거부한다(다른 용도 토큰을 로그인에 못 쓰게 하려고). 내 수정안은 그 둘을 동시에 요구했다.

▶ 실제 출력 — 반박의 실측

```
require = ['exp','ver','sub','purpose']
  로그인 토큰  →  거부: missing 'purpose'
  (그런데 purpose를 넣으면 기존 검사가 거부한다)
  → 교집합이 공집합. 어떤 토큰도 통과 못 한다.
```

**⚠️ 함정** — 배포되면 전원이 로그아웃되고, **다시 로그인해도 401**이며, 관리자 화면도 같이 죽어서 **되돌릴 방법이 코드 재배포뿐**이었다.

그런데 그 제안이 노렸던 실질은 **한 단어**였다. 토큰의 버전 항목을 읽을 때 '없으면 0으로 친다'로 돼 있었는데, 그러면 **항목이 아예 없는 위조 토큰이 0으로 채워져** 버전이 0인 모든 계정과 일치했다. 대괄호 하나로 닫혔다.

> **🔎 비유** 출입증에 '몇 번째 재발급본인지' 칸이 있는데, 칸이 비어 있으면 '0번째'로 간주하고 통과시켰던 것이다. 위조범은 그 칸을 그냥 안 쓰면 됐다.

## 6. 보안 검사 — 그리고 아침에 고친 병을 저녁에 또 밟았다

"보안검사는 자세히 해본 거지?"라는 질문을 받고, 오늘 쓴 코드 밖까지 다시 봤다 — 권한 경계, 공급망과 시크릿, 그리고 입력 경로.

▶ 실제 출력 — 깨끗했던 것

```
권한 상승·IDOR:        0건 (엔드포인트 45개 전수 대조)
npm audit:             0건
pip-audit:             0건 (85개 실검사)
gitleaks:              0건 (277 커밋)
개발일지 docx 29개:    0건 (압축을 직접 풀어서 확인)
라이브 보안 헤더 6종:  선언과 실제가 문자열까지 일치
```

나온 건 다른 종류였다 — **로그인 없이 서버 오류를 만들 수 있는 입구 다섯 개.**

그중 하나가 뼈아팠다. 아침에 나는 검색어에 특수한 바이트가 들어오면 서버가 500을 내는 걸 고쳤고, 커밋 메시지에 **'고친 자리 옆의 안 쓸린 입구'**라고 적었다. 그런데 **같은 파일의 글쓰기 경로는 안 봤다.** 저녁 검사가 같은 병을 다섯 군데 더 찾았다 — 익명 댓글, 글 제목, 태그, 푸시 구독, 결제.

**⚠️ 함정** — 교훈을 적는 것과 교훈이 몸에 붙는 것 사이의 거리를, 오늘은 **같은 날 안에서** 확인했다.

그래서 이번엔 필드마다 막지 않았다. 요청 본문 스키마들의 **공통 기반**에서 한 번에 걸렀다. 필드가 늘어도 자동으로 덮인다.

가장 넓었던 입구는 따로 있었다. 숫자가 아닌 값(무한대)을 아무 필드에나 넣으면, 서버가 **'잘못된 입력입니다' 응답을 만들다가** 터졌다. 오류 응답에 문제의 입력값을 그대로 담는데 그 값이 응답 형식으로 표현되지 않기 때문이다.

▶ 실제 출력 — 실측 — 요청 25번 반복

```
{"email": <무한대>, ...}   →  500 × 25   (429 없음)
{"email": "a@b.com", ...}  →  401 × 10 → 429 × 15
```

아래 줄이 정상 동작이다. 열 번 실패하면 '너무 잦다'며 막는다. **윗줄은 그 차단을 지나쳐 간다** — 검증이 차단 장치보다 먼저 도는 층에서 터지기 때문이다. 그래서 이건 '오류 메시지가 못생겼다'가 아니라 **차단 장치를 무력화하는 입구**였다.

## 7. 틀린 전제 두 개

검사는 결함만 찾은 게 아니라 내가 **근거 없이 믿고 있던 것**도 두 개 깼다.

**전제 1** — "이 프로젝트는 전송량이 곧 비용이니 파일 크기를 아껴야 한다" — 실측하니 지난 30일 요청 19,886건 / 전송 26.5MB였다. 무료 한도의 0.0026%다. 크기 최적화는 여기서 값을 못 한다.

**전제 2** — "내 커밋 메시지의 숫자는 정확하다" — '번들 +3.3KB'라고 적었는데 그건 자바스크립트만이었다. 같은 커밋에서 스타일시트가 +2.6KB 늘었고 나는 그걸 안 봤다. 그리고 그 증가의 60%는 복사 버튼 하나가 만든 것이었다.

두 번째가 특히 재미있다. 자바스크립트 크기만 보면 그 버튼은 508바이트짜리 작은 변경인데, 스타일까지 세면 1,559바이트로 **세 배**다. **어디를 재느냐가 결론을 바꾼다.**

## 8. 오늘 하루의 숫자

▶ 실제 출력 — 정리

```
배포:        미배포 8커밋 + 의존성 1건
발행:        개발일지 #29 (공개 글 29건 / 연재 29편)
첫 화면:     콘텐츠 노출 0% → 29편 · 24만 자
붙인 기능:   공유 · 코드 복사 · 404 · 공유 카드(1200×630)
검사:        8갈래 + 보안 3갈래, 반박 2회
고친 결함:   프론트 6건 + 백엔드 6건
기각한 수정: 6건 (내 제안 5건 포함)
테스트:      프론트 35 → 49 · 백엔드 310 → 318
커버리지:    86.92% → 87.21%
```

'기각한 수정 6건'이 오늘 가장 마음에 드는 줄이다. 그중 다섯이 내가 낸 것이고, 둘은 그대로 나갔으면 사고였다.

## 9. 아직 안 끝난 것

정직하게 남긴다. 오늘 닫지 못한 것들이다.

- **감시가 살아났는지 아직 모른다.** 권한은 고쳤지만, 그 뒤로 예정된 실행이 아직 안 돌았다. 지금은 '설정했다'까지다 — 오늘 배운 것을 그대로 적용하면, 초록을 보기 전까지는 고쳤다고 말하면 안 된다.
- **로그아웃이 서버에 없다.** 토큰을 무효화하는 장치는 이미 있는데 그걸 당길 손잡이가 없다. 다만 이건 백엔드 세 줄이 아니다 — 인증 만료를 화면이 제대로 처리하는 코드가 한 곳뿐이라, 손잡이만 붙이면 다른 기기가 '로그인된 것처럼 보이는데 아무것도 안 되는' 상태가 된다.
- **배포가 자기 결과를 검증하지 않는다.** 배포 절차 어디에도 '나간 것이 실제로 서빙되는가'를 확인하는 줄이 없다. 오늘 만든 것 전체가 그 사각 위에 얹혔다.
- **레이아웃 수정은 눈으로 못 봤다.** 코드블록을 감싸면서 여백 규칙이 어긋나는 걸 계산으로 찾아 고쳤는데, 이 환경엔 브라우저가 없어 실제 화면을 확인하지 못했다.
