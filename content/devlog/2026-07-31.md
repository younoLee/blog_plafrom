# 블로그 만들기 #23 — 적어놓은 것과 실제로 돌고 있는 것

> 입문자가 읽어도 이해되게 — '기능을 지운다'가 왜 코드 한 곳 지우는 걸로 안 끝나는지, 같은 상태 코드가 왜 증명이 못 되는지, 그리고 AWS에 낼 서류 한 장이 어떻게 코드 검사로 이어지는지 위주로.

## 0. 오늘 한 일 한눈에

## 1. 2주 동안 반쪽만 살아 있던 기능

이 블로그에는 원래 두 종류의 '구독'이 있었다.

- **뉴스레터 구독** — 이메일 주소만 넣으면 새 글 알림을 받는 것 (로그인 불필요)
- **계정 구독** — 로그인해서 특정 글쓴이를 구독하고, 그 사람이 승인하면 알림을 받는 것

7월 18일에 이 둘을 **계정 구독 하나로 합치기로** 했다. 뉴스레터는 없애기로 한 것이다. 그런데 오늘 확인해보니 그 작업이 절반만 끝나 있었다.

▶ 실제 출력 — Subscriber(뉴스레터) 테이블을 쓰는 코드를 전부 찾아보니

```
app/routers/subscribers.py    구독 신청을 받아 저장하고 확인 메일을 보냄
app/routers/subscribers.py    확인 링크를 눌렀는지 처리함
…그리고 끝. **발송에 쓰는 코드가 없다.**
새 글 알림(notify_new_post)이 실제로 보는 것:
    select(User.email) ... join(AuthorSubscription)   ← 계정 구독
```

**화면과 발송은 갈아탔는데 수집만 남아 있었다.** 즉 지금 뉴스레터를 구독하면, 주소를 받아서 확인 메일을 보내고, 확인을 눌러도 **그 뒤로 아무것도 오지 않는다.**

**⚠️ 함정** — 기능을 '없앤다'고 할 때 화면에서 버튼을 지우는 걸로 끝내면 이렇게 된다. 버튼은 안 보이는데 그 버튼이 부르던 주소는 그대로 열려 있고, 아무도 안 보는 곳에 데이터가 계속 쌓인다. 실제로 주소 4개가 쌓여 있었다.

## 2. 도착할 수 없는 메일을 '보냈다'고 말하고 있었다

여기에 두 번째 문제가 겹쳐 있었다. 이 블로그의 메일은 AWS의 SES라는 서비스로 나가는데, 이 계정은 아직 **샌드박스**(연습 모드)다. 샌드박스에서는 **미리 등록한 3개 주소로만** 메일이 나간다. 그 밖으로는 발송 자체가 거부된다.

그럼 모르는 사람이 뉴스레터를 구독하면 어떻게 될까? 메일 서버를 꺼놓고 실제로 재봤다.

▶ 실제 출력 — 메일이 나갈 수 없는 상태에서 구독 신청

```
curl -X POST http://localhost:8000/api/subscribers -d '{"email":"stranger@example.com"}'
HTTP=200   {"message":"확인 메일을 보냈어. 메일함에서 구독 확인을 눌러줘."}
서버 로그:
  INFO:  "POST /api/subscribers HTTP/1.1" 200 OK      ← 접근 로그는 성공
  (그 옆에 처리되지 않은 트레이스백만 덩그러니)
```

**방문자는 성공 메시지를 받는다.** 그리고 아무것도 오지 않는다. 영원히.

왜 200이 나가느냐면, 메일 발송을 '응답을 보낸 뒤에' 백그라운드로 처리하기 때문이다. 응답은 이미 나간 뒤라 실패를 알릴 방법이 없다.

> **🔎 비유** 우체통에 편지를 넣는 순간 '배달 완료' 도장을 찍어주는 것과 같다. 실제로 그 편지가 반송돼도 도장은 이미 찍혀 있다.

> **🛠 전문가 노트** 이 저장소가 반복해서 만나는 병이다. #18에서는 빈 값을 초록으로 보고했고, #22에서는 해석기 고장을 '예산이 0개다'로 승격시켰다. 전부 같은 모양 — **실패가 성공으로 보이는 것.** 그냥 실패보다 나쁘다. 없으면 모르는 줄 알지만, 틀리면 아는 줄 안다.

## 3. 떼어냈더니 SES 문제가 같이 사라졌다

그래서 뉴스레터 구독을 폐지했다. 공개 엔드포인트 4종과 확인 메일 발송 함수, 프론트의 확인 페이지와 안 쓰는 API 함수들을 지웠다. **관리자용 조회·삭제만 남겼다** — 이미 쌓인 주소는 개인정보라, 폐지했다고 지울 방법까지 없애면 곤란하다.

그런데 여기서 예상 못 한 이득이 나왔다. 이 앱에서 **'검증 안 된 임의의 주소'로 메일이 나가던 경로가 그것 하나뿐**이었던 것이다.

▶ 실제 출력 — 남은 메일이 가는 곳

```
가입 인증      → 초대제라 사실상 잠김 (공개 가입이 403)
비번 재설정    → 등록된 계정 주소
새 글 알림     → 등록된 계정 주소
→ 전부 '우리가 초대한 사람'이다. 그 수는 유한하다.
```

그러면 **SES 샌드박스를 벗어나지 않아도** 된다. 그 주소들만 등록해두면 다 동작하니까. 기능 하나를 떼었더니 인프라 숙제가 같이 없어진 셈이다.

> **🛠 전문가 노트** 문제를 푸는 방법이 항상 '더 만드는 것'은 아니다. 오늘의 SES 문제는 코드를 추가해서가 아니라 **쓰지도 않는 기능을 걷어내서** 풀렸다.

## 4. 준비해둔 서류의 논거 두 개가 그 사이 거짓이 됐다

SES 샌드박스를 벗어나려면 AWS에 사유서를 내고 심사를 받아야 한다. 이 계정은 7월 22일에 이미 **한 번 거부**당했고, 그때 다시 낼 사유서를 준비해뒀었다.

그 사유서를 오늘 다시 읽어보니 **두 문장이 더 이상 사실이 아니었다.**

▶ 실제 출력 — 준비해둔 사유서 vs 지금

```
주장 ①  "방문자가 가입 폼을 제출하면 인증 메일을 보낸다"
  → 7월 28일에 가입을 초대제로 닫았다. 지금은 403이다.
주장 ②  "뉴스레터 더블 옵트인으로 수신 동의를 받는다"
  → 오늘 폐지했다. 그 엔드포인트 자체가 없다.
```

**⚠️ 함정** — 그대로 냈으면 AWS에 **사실과 다른 진술**을 하는 것이다. 그리고 이건 상대가 직접 확인할 수 있는 종류의 거짓이다 — 사이트를 열어 가입 버튼을 찾아보면 되니까.

그래서 처음부터 다시 썼다. 흥미로운 건 **바뀐 사실이 오히려 유리하다**는 점이다. 공개 가입이 없고 목록 메일이 0이면 반송·불만 위험이 구조적으로 거의 없다 — 심사가 보려는 게 정확히 그거다. 논지가 '누구나 가입하게 해달라'에서 '초대한 사람에게만 보낸다'로 바뀌었다.

## 5. 서버를 켜지 않고 실제 숫자를 셌다

사유서에는 '계정이 몇 개인지'를 구체적으로 써야 한다. 그런데 이 블로그는 평소 서버를 꺼둔다(비용 때문에). 숫자를 재려고 서버를 켜야 하나?

안 켰다. **매일 서버를 끌 때 뜨는 백업**이 S3에 있고, 마지막 백업은 서버를 끈 시점 그대로다 — 그 뒤로 서버가 안 켜졌으니 지금 상태와 같다. 그걸 로컬 데이터베이스에 임시로 복원해서 조회하고 지웠다.

▶ 실제 출력 — 백업에서 센 실제 숫자

```
users_total      6
notify_on        0        ← 새 글 알림을 켠 사람이 아무도 없다
approved_subs    3
계정 내역:
  es2646526@gmail.com     admin    ← SES에 이미 등록됨
  jinukkim0305@naver.com  writer   ← SES에 이미 등록됨
  youno3249@gmail.com     writer   ← SES에 이미 등록됨
  demo@example.com        writer   (데모 계정)
  test@test.com           pending  (쓰레기)
  ppap@gmail.com          pending  (쓰레기)
```

**이 숫자가 신청 논거를 약하게 만들었다.** 실제 사람 3명이 전부 이미 SES에 등록돼 있다. 즉 지금 이 순간 메일을 못 받는 사람은 아무도 없다. '지금 막혀 있다'로 쓸 수가 없는 것이다.

그래서 사유서에 이 문장을 일부러 넣었다.

▶ 실제 출력 — 사유서 본문에서

```
Why we are asking: we are not currently blocked, and we want to be
straightforward about that.
  (지금 막혀 있지는 않다. 그 점을 솔직히 밝힌다.)
```

> **🛠 전문가 노트** 숨기고 통과시키면 나중에 그 한 줄 때문에 전체를 의심받는다. 약한 논거는 약한 대로 쓰는 게 낫다. 대신 진짜 논거를 정확히 댔다 — 초대받은 사람이 우리 메일을 받기도 전에, 자기와 아무 관계 없는 AWS 계정의 확인 메일을 먼저 찾아 눌러야 한다는 것.

## 6. 오늘의 백미 — 403이 맞는데 막은 놈이 달랐다

사유서 첫 문단이 '공개 가입은 닫혀 있다'인데, 그게 프로덕션에서 진짜인지 확인해야 했다. 서버를 켜서 가입 요청을 직접 던졌다.

▶ 실제 출력 — 가입 요청 (1차)

```
POST /api/auth/register  {"email":"probe-check@example.com", ...}
status 403  {"detail":"Forbidden"}
```

403이다. 닫혀 있다는 뜻이니 확인 끝 — 이라고 넘어갈 뻔했다.

그런데 응답 문구가 이상했다. 우리 가입 게이트가 내는 메시지는 한국어로 "가입은 현재 초대제로 운영됩니다"인데, 나온 건 영어 `Forbidden`이었다.

**다른 검사가 막은 것이었다.** 이 서버는 CDN을 거치지 않은 요청을 차단하는 '오리진 시크릿' 검사가 앞단에 있다. 나는 서버 안에서 직접 불렀으니 그 헤더가 없었고, 가입 게이트까지 **가보지도 못하고** 그 앞에서 튕긴 것이다.

▶ 실제 출력 — 시크릿을 붙여 다시 (2차)

```
POST /api/auth/register  + X-Origin-Secret: ***
status 403  {"detail":"가입은 현재 초대제로 운영됩니다. 관리자에게 문의하세요."}
```

**⚠️ 함정** — **상태 코드가 같아도 이유가 다르면 증명이 아니다.** 1차에서 멈췄으면 '가입이 닫힌 걸 확인했다'고 AWS에 적었을 텐데, 실제로 확인한 건 '오리진 시크릿이 동작한다'였다. 둘 다 사실이지만 내가 증명하려던 건 그게 아니다.

> **🔎 비유** 문이 안 열려서 '잠겼구나' 했는데, 사실은 그 앞 복도 문이 잠겨 있어서 정작 확인하려던 문 앞까지 가보지도 못한 것이다.

> **🛠 전문가 노트** 검사할 때 '기대한 결과가 나왔다'로 멈추면 안 되는 이유다. **왜 그 결과가 나왔는지**까지 봐야 한다. 이번엔 응답 본문의 언어가 달라서 눈치챘다.

## 7. 사유서에 '지웠다'고 썼는데 프로덕션엔 살아 있었다

뉴스레터를 폐지하고 사유서에 이렇게 적었다.

▶ 실제 출력 — 사유서 본문

```
We removed our newsletter subscription feature entirely on 2026-07-31,
including the endpoint that accepted addresses
  (엔드포인트까지 통째로 제거했다)
```

제출 직전에 확인차 프로덕션의 그 주소를 직접 불러봤다.

▶ 실제 출력 — 프로덕션에 실제로 물어보니

```
POST /api/subscribers  (오리진 시크릿 포함)
status 200  {"message":"확인 메일을 보냈어. 메일함에서 구독 확인을 눌러줘."}
```

**살아 있었다.** 코드는 고쳤고 커밋도 했지만, 프로덕션 서버는 아직 옛 이미지로 돌고 있었다. 이 프로젝트는 백엔드 배포를 사람이 직접 하기 때문이다.

**⚠️ 함정** — 그 상태로 제출했으면 사유서가 거짓이었다. 그리고 **AWS가 직접 부딪혀 확인할 수 있는** 종류의 거짓이다 — 주소 하나 부르면 되니까. 순서가 뒤집히면 안 됐다: 배포가 먼저고 제출이 나중이다.

재빌드하고 다시 쟀다.

▶ 실제 출력 — 배포 후 (이미지 2026-07-31T06:57Z · healthy)

```
POST /api/subscribers             200 → 405
POST /api/subscribers/confirm          405
POST /api/subscribers/unsubscribe      405
GET  /api/subscribers/me               405
GET  /api/status   200  {"posts":21,"subscribers":2}
```

> **🛠 전문가 노트** `subscribers: 2`도 검증 지점이다. 폐지된 테이블은 지금 0건이라, 옛 코드였으면 0이 나왔어야 한다. 2가 나왔다는 건 **계정 구독 인원을 세는 새 쿼리가 돈다**는 뜻이다. 숫자 하나가 '어느 버전이 돌고 있는지'를 알려준 셈이다.

404가 아니라 405(메서드 없음)인 이유는, 관리자용 조회·삭제가 같은 주소에 남아 있어서 주소는 맞고 메서드만 없기 때문이다. 회귀 테스트를 상태 코드가 아니라 **'성공하지 않는다'**로 써둔 판단이 여기서 값을 했다.

## 8. 자동 배포가 6초 만에 빨간불 — 고장이 아니라 안전장치

커밋을 올리자 프론트엔드 자동 배포가 6초 만에 실패했다.

▶ 실제 출력 — GitHub Actions 로그

```
::error:: 이 push에 백엔드 코드 변경이 함께 있습니다.
          프론트를 먼저 배포하면 아직 없는 API를 호출하게 됩니다.
→ scripts/deploy_backend.sh 로 백엔드를 먼저 배포한 뒤,
  이 워크플로를 수동 실행하세요.
```

이건 고장이 아니라 **7월 11일에 실제로 겪고 만든 장치**다. 프론트는 자동 배포인데 백엔드는 사람이 손으로 한다. 그래서 한 번에 둘 다 올리면 프론트가 먼저 나가서 아직 존재하지 않는 API를 부른다.

이번엔 백엔드를 이미 배포해둔 뒤였으니 실제로는 안전했다. 그래서 프론트만 건드리는 커밋을 따로 올려 통과시켰다.

> **🛠 전문가 노트** 안전장치가 '틀리게' 막는 것과 '설계대로' 막는 것을 구분해야 한다. 빨간불을 보자마자 장치를 끄는 습관이 들면, 진짜로 막아야 할 때 아무도 안 듣는다. 이번 빨간불은 **정확히 제 일을 한 것**이다.

## 9. 문서에 적어둔 '관리자 화면'이 존재하지 않았다

뉴스레터를 폐지하면서 관리자용 조회·삭제를 남긴 이유를 이렇게 적었다 — "이미 쌓인 주소는 개인정보라 관리자 화면에서 지울 수 있게 남긴다."

그런데 프론트엔드를 확인해보니 **그 화면이 없었다.**

▶ 실제 출력 — 프론트에서 구독자 API를 쓰는 곳 찾기

```
$ grep -rn 'api/subscribers' src --include=*.ts --include=*.tsx
  (아무것도 안 나옴)
$ grep -n '구독자' src/pages/AdminPage.tsx
  (아무것도 안 나옴)
```

`frontend/src/api/subscribers.ts`는 함수가 여럿 있는데 **아무도 import하지 않는 죽은 코드**였다. 관리자 페이지에 구독자 UI 자체가 없다. 그러니 '관리자 화면에서 지운다'는 내 문장은 처음부터 틀린 말이었다. (실제로 오늘 4개를 지운 것도 데이터베이스로 직접 했다.)

죽은 파일은 지우고, 문서의 그 문장도 고쳤다.

**⚠️ 함정** — 내가 방금 쓴 문서가 나를 속인 경우다. '이렇게 하면 된다'고 적을 때는 **그 경로가 실제로 있는지** 한 번 밟아봐야 한다. 안 밟아보고 적으면 그건 계획이지 사실이 아니다.

## 10. 신청 버튼이 셋 중 둘이 죽어 있었다

서류는 다 됐으니 내기만 하면 됐다. 그런데 낼 방법을 찾는 데만 한참 걸렸다.

▶ 실제 출력 — 신청 경로 세 개를 다 눌러본 결과

```
① SES 콘솔의 '프로덕션 액세스 요청' 버튼
     → ConflictException
     (이 버튼이 부르는 API가 '심사 이력이 있으면' 거부한다.
      첫 신청 때 됐던 건 이력이 없어서였다)
② 거부된 옛 케이스에 회신
     → 케이스가 닫혀 있어 회신 버튼이 없음
③ 명령줄로 지원 케이스 생성
     → SubscriptionRequiredException (유료 지원 플랜 전용)
④ 지원 센터에서 '서비스 한도 증가' 케이스를 새로 생성
     → ✅ 이건 된다. 무료 플랜에서도 한도 증가 케이스는 열린다
```

그리고 그 폼에 마지막 함정이 있었다. **필수 항목인 '한도 유형'에 고를 수 있는 값이 `Desired Dedicated IP`(전용 IP) 하나뿐**이었다. 우리가 원하는 건 전용 IP가 아니라 샌드박스 해제인데, 폼이 그걸 표현하지 못한 것이다.

고를 수밖에 없으니 골랐다. 대신 본문 맨 앞에 이 문단을 넣었다.

▶ 실제 출력 — 본문 첫 문단에 추가한 것

```
IMPORTANT - please read this first, the form could not express our
request. This support form required a "Limit Type" and the only value
it offered was "Desired Dedicated IP". We are NOT requesting a
dedicated IP address... We are requesting removal of the sending
sandbox for this account in ap-northeast-2.
```

> **🛠 전문가 노트** **폼이 의도를 표현하지 못하면 본문에서 명시적으로 부정한다.** 이 한 줄이 없으면 심사자가 '전용 IP 요청'으로 읽고 엉뚱한 답을 준다. 그리고 전용 IP는 유료다 — 안 부정했으면 원치 않는 것에 대한 답을 받았을 것이다.

## 11. 오늘 배운 것

### ① 기능을 지우는 건 한 층이 아니라 여러 층이다

코드에서 지웠다 / 커밋했다 / 배포했다 / 화면에서 사라졌다 — 넷이 전부 다른 사건이다. 오늘 이 넷이 다 어긋난 순간이 한 번씩 있었다.

### ② 상태 코드가 같아도 이유가 다르면 증명이 아니다

403을 받고 '가입이 막혔다'고 결론 낼 뻔했는데, 실제로 막은 건 그 앞의 다른 검사였다. 기대한 답이 나왔을 때 오히려 한 번 더 물어야 한다.

### ③ 문제를 푸는 방법이 항상 '더 만드는 것'은 아니다

SES 숙제는 코드를 추가해서가 아니라 쓰지도 않는 기능을 걷어내서 풀렸다. '검증 안 된 주소로 메일이 나가는 경로'가 0이 되니까 문제 자체가 없어졌다.

### ④ 약한 논거는 약한 대로 쓴다

실측해보니 신청 논거가 생각보다 약했다. 숨기지 않고 "지금 막혀 있지는 않다"를 본문에 직접 썼다. 숨기고 통과시키면 그 한 줄 때문에 전체를 의심받는다.

### ⑤ 내가 쓴 문서도 검증 대상이다

"관리자 화면에서 지울 수 있다"고 적어놓고 보니 그 화면이 없었다. 적을 때 그 경로를 한 번 밟아봤으면 안 썼을 문장이다.

## 12. 오늘의 숫자

▶ 실제 출력 — 전 → 후

```
커밋            10개 (전부 푸시 완료)

커버리지        80.78% → 80.81%

```

## 13. 정직하게 남기는 것

- **AWS 답변은 아직 안 왔다.** 승산은 반반으로 본다 — '3명뿐이면 그냥 등록하시라'는 답이 올 수 있고, 그 반박이 틀린 말도 아니다
- **거부돼도 잃을 게 없다.** 지금 상태 그대로이고, 지금 상태에서 아무도 막혀 있지 않다. 다리를 먼저 놓고 신청한 이유가 이것이다
- **개발일지 발행은 아직.** 문서는 만들었지만 블로그에 올리려면 서버를 켜야 한다
- **새 글 알림을 켠 사람이 0명이다.** 기능은 있는데 아무도 안 쓴다 — 다음에 볼 것
- **Web Push를 다음 작업으로 잡았다.** 새 글 알림을 브라우저 푸시로 옮기면 메일이 아예 안 끼어들어 SES 판돈 자체가 줄어든다. 다만 iOS는 홈 화면에 추가해야만 되는 한계가 있다
