# 블로그 만들기 #28 — 고친 자리 옆에 안 쓸린 입구가 있다

> 입문자가 읽어도 이해되게 — '이건 고쳤다'는 주석이 왜 위험할 수 있는지, 3MB짜리 폰트가 어떻게 640KB짜리 자바스크립트 논쟁을 무의미하게 만드는지, 그리고 '아무나 관리자 이름으로 댓글을 달 수 있다'가 어떻게 가능했는지 위주로.

## 1. 아침 — 재건할 때마다 사람이 5번 정확해야 했던 자리

2026-07-27에 서버를 진짜로 삭제하고 되살리는 훈련을 했었다. 그때 나온 결함 중 하나가 **F5**였다. 서버를 새로 만들면 ID가 바뀌는데, 그 ID가 스크립트 5개에 문자열로 박혀 있었다.

▶ 실제 출력 — 고치기 전 — 다섯 파일에 같은 값이 박혀 있었다

```
scripts/watch.sh:34          INSTANCE_ID=i-0abd...
scripts/stop_server.sh:30    INSTANCE_ID=i-0abd...
scripts/deploy_backend.sh:26 INSTANCE_ID=i-0abd...
scripts/env_escrow.sh:31     INSTANCE_ID=i-0abd...
scripts/restore_drill.sh:43  INSTANCE_ID=i-0abd...
```

안 고치면 정지 절차도, 훈련도, 감시도 **존재하지 않는 서버를 들여다본다.** 그리고 감시가 그러면 조용히 실패한다 — 아무 일도 안 일어나는 게 정상처럼 보인다.

> **🔎 비유** 이사할 때마다 명함·계약서·택배 주소·병원 차트·은행 등록 주소를 손으로 다섯 번 고쳐야 하는 것과 같다. 다섯 번 중 한 번을 빠뜨리는 건 시간문제이고, 빠뜨린 게 어디인지는 사고가 나야 안다.

고친 방식은 '주소를 잘 관리하자'가 아니라 **'주소를 안 적는다'**이다. 이름표(태그)로 찾게 했다. 그러면 이사를 해도 고칠 파일이 0개다.

### 그런데 그 검사 자체가 절반만 지키고 있었다

이 저장소에는 '런북과 코드가 어긋났는지' 보는 검사가 있고, 그 안에 "스크립트 5개의 ID가 전부 같은가"라는 항목이 있었다. 오늘 그 뜻을 뒤집었다.

> **🛠 전문가 노트** 그 검사는 **손으로 5곳을 고치는 절차를 전제한** 검사였다. 즉 F5를 없애는 게 아니라 'F5를 반만 지키고 있는지'를 감시하고 있었다. 이제는 '박혀 있는가'를 본다 — 박혀 있으면 그 자체가 실패다.

## 2. '안 한 일'이 3건인 줄 알았는데 7건이었다

어제 편의 주제가 그거였는데, 오늘 코드로 다시 재보니 더 있었다. 가장 나쁜 둘만 적는다.

### ① 고친 그 커밋이 '안 고쳤다'고 적었다

문서에 "이 버그는 **미적용**, 잠재버그로 남김"이라고 적혀 있었다. 코드를 보니 이미 고쳐져 있었고, 그걸 고친 커밋을 찾아보니 —

▶ 실제 출력 — git이 알려준 것

```
$ git show --stat 9ae515e
9ae515e 2026-07-24 fix+docs: ECS 이전 실배포 마무리 — env.py % 버그, ...
 backend/alembic/env.py      |  6 ++++-      ← 고친 파일
 docs/ecs-stage6-evidence.md | 60 ++++++++    ← '미적용'이라고 적은 파일
```

**같은 커밋이다.** 고친 손과 기록한 손이 같은 커밋 안에 있었는데도 어긋났다. 그래서 이건 '나중에 낡았다'로 변명이 안 된다 — **태어날 때부터 틀린 문장**이다. 그 대가로 2주 반 동안 있지도 않은 잠재버그가 백로그에 살아 있었다.

### ② 한 문서가 자기 자신을 반박하고 있었다

로드맵 73줄이 "이 게이팅은 미적용"이라고 말하는데, **같은 파일 92줄**이 "08-09 오전에 이 줄을 '미적용'으로 적었는데 틀린 서술이었다"고 정정해두고 있었다.

**⚠️ 함정** — 정정을 **밑에 새 줄로 추가**했기 때문이다. 그러면 낡은 줄이 안 죽는다. 아래를 안 읽고 위만 읽은 사람은 여전히 "타깃 없이 apply하면 월 $50짜리 인프라가 살아난다"고 믿게 된다. **정정은 원문 자리에서 해야 한다.**

## 3. 훈련이 19일 동안 '지난달'을 증명하고 있었다

백업이 실제로 복원되는지 확인하는 훈련이 있다. 마지막 전체 실행이 07-22였고, 그때 대상은 테이블 12개였다. 그 뒤로 셋이 늘어 지금은 15개다.

훈련은 그동안 **한 번도 빨간불이 아니었다.** 돌리지 않았으니까. 즉 이 훈련은 19일 동안 "지난달 스키마가 복원되는가"를 증명한 상태로 멈춰 있었다.

> **🛠 전문가 노트** **훈련도 썩는다. 다만 초록으로 썩는다.** 코드가 낡으면 테스트가 빨개지지만, 검사 자체가 낡으면 아무 신호도 안 난다 — 안 돌린 검사는 실패하지도 않기 때문이다.

▶ 실제 출력 — 오늘 돌린 결과

```
OK   테이블 집합       15개 전부 일치
OK   인덱스 수          47
OK   제약 수             112
OK   시퀀스              14개 전부 max(id) 이상
OK   INSERT/DELETE 성공 (새 id=11)
OK   복원된 암호문이 현재 키로 풀린다      ← 07-27부터 열려 있던 미검증
```

### 행 수로는 원리적으로 못 잡는 손실

마지막 줄이 오늘의 수확이다. 이 블로그는 사용자가 자기 AI 키를 넣을 수 있고, 그 키는 **암호화해서** DB에 저장한다. 그런데 **암호를 푸는 열쇠는 백업 안에 없다** — 서버 설정에만 있다.

> **🔎 비유** 금고를 통째로 백업했는데 열쇠는 백업 안에 안 넣은 것과 같다. 복원하면 금고는 완벽하게 돌아온다. 열리지만 않을 뿐이다.

그래서 "행 수가 맞다"로는 절대 못 잡는다. **복원 성공률 100%와 데이터 전손이 동시에 성립하는 자리**다. 세지 말고 실제로 풀어봐야 한다.

**⚠️ 함정** — 그런데 이 검사는 **암호문이 0건이면 조용히 건너뛰고 있었다.** 그래서 07-27에 '증명 못 했다'고 남긴 항목이 매번 초록 속에서 2주를 살아남았다. 오늘 그 줄을 경고로 바꾸고, 닫는 방법까지 출력하게 했다. **검사를 안 한 것이 검사한 것처럼 읽히는 게 실패보다 나쁘다.**

## 4. 오후 — 에이전트 다섯을 붙여 성능을 뒤졌다

"병목 같은 부정적인 걸 심층적으로 찾아달라"는 요청이었다. 다섯 갈래(DB·API 동시성·프론트엔드·인프라·조용한 실패)를 동시에 돌리고, 나온 지적을 **내가 직접 재확인**했다.

> **🛠 전문가 노트** 에이전트를 여럿 쓸 때 중요한 건 개수가 아니라 **서로 심문시키는 것**이다. 오늘 나온 지적 중 7건은 에이전트가 스스로 철회했다 — 근거가 얇거나, 이미 다른 장치가 덮고 있거나, 사실관계가 틀려서. 목록이 긴 것보다 정확한 게 낫다.

### ① 폰트가 자바스크립트보다 다섯 배 컸다

번들 크기(640KB)를 어떻게 줄일지 이야기하고 있었는데, 실제로 회선에 나가는 건 폰트였다.

▶ 실제 출력 — curl로 직접 재본 것

```
$ curl -sI https://cdn.jsdelivr.net/.../static/woff2/Pretendard-Regular.woff2
HTTP/2 200
content-length: 765892        ← 웨이트 하나가 748KB
```

코드가 쓰는 굵기가 넷(보통·중간·약간굵게·굵게)이라 **합치면 약 3MB**다. 브라우저용으로 잘라놓은 판본이 따로 있는데 잘라놓지 않은 쪽을 부르고 있었다.

> **🔎 비유** 사전을 찾는데 필요한 낱말 몇 개 때문에 **사전 전권을 통째로** 배달받은 것과 같다. 출판사는 낱말별로 쪼갠 판본도 팔고 있었다.

**⚠️ 함정** — 고치면서 하마터면 '고쳤는데 안 고쳐진' 상태를 만들 뻔했다. 쪼갠 판본은 폰트 이름이 다르다 — CSS의 이름 목록을 같이 안 고치면 **브라우저가 그 폰트를 못 찾아 시스템 기본 글꼴로 떨어진다.** 화면이 그럭저럭 보여서 알아채기도 어렵다.

### ② 160KB짜리 코드 색칠 도구가 아무 일도 안 하고 있었다

코드블록에 색을 입히는 라이브러리가 들어 있었다. 그런데 이 블로그의 글은 코드블록에 **언어 표시를 안 붙인다.** 그 라이브러리는 언어 표시가 없으면 그냥 넘어간다.

▶ 실제 출력 — 직접 세어본 것

```
$ grep -rcE '^[ \t]*```' content/devlog/*.md | 합계
260                       ← 코드블록 총 260개
$ grep -rnE '^[ \t]*```[A-Za-z]' content/devlog/*.md | wc -l
0                         ← 언어가 붙은 것: 0개
$ grep -ro 'language-[a-z]*' (렌더 결과) | wc -l
0                         ← 실제로 색칠된 것: 0개
```

**한 블록도 색칠하지 않으면서 160KB를 지고 있었다.** 빼도 화면이 전혀 안 변한다.

▶ 실제 출력 — 빼고 나서

```
빼기 전 : 640,255 bytes   (gzip 194,087)
빼고 나서: 472,980 bytes   (gzip 143,640)
차이     : −167 KB
```

### ③ 요청 하나가 서버 전체를 112초 멈출 수 있었다

이미지 업로드 처리에 문제가 있었다. 파이썬 웹서버는 '동시에 여러 요청을 처리하는 방식'이 두 가지인데, 이 함수 하나만 다른 방식으로 쓰여 있었고 그 안에서 **느릴 수 있는 작업**을 했다.

> **🔎 비유** 은행 창구가 여럿인데, 어떤 손님 한 명이 **번호표 기계 앞에 서서** 일을 보기 시작한 것과 같다. 창구는 비어 있는데 아무도 번호표를 못 뽑는다.

▶ 실제 출력 — 실제로 재본 최악의 경우

```
예외: EndpointConnectionError
도달불가 저장소에 업로드 시도 → 112.3초
```

그동안 **서버 상태 확인 응답조차 못 나간다.** 그래서 약 95초 뒤에는 "이 서버는 죽었다"고 판정돼 버린다. 동시 접속자가 필요 없다 — **요청 1개면 된다.**

### ④ '고쳤다'고 적힌 주석 옆의 안 쓸린 입구

여기서 오늘의 주제가 처음 또렷해졌다. 서버 코드에 이런 주석이 있다.

▶ 실제 출력 — main.py의 주석 (요약)

```
"""DB에 못 붙으면 500이 아니라 503으로 답한다.
 2026-07-28 훈련에서 DB를 내려보니 전부 500이 text/plain으로 나갔다.
 프론트는 JSON을 기대하므로 파싱조차 못 한다 ... 503으로 바꾸면 안내 경로를 탄다."""
```

맞는 말이고 실제로 고쳐져 있다. 그런데 **DB 연결이 부족해서 못 쓰는 경우**는 그 처리에 안 걸린다 — 파이썬이 던지는 오류의 '종류'가 다르기 때문이다. 그래서 그 입구로 들어오면 여전히 옛날 그대로 500이 나갔다.

▶ 실제 출력 — 실제로 재현하고, 고친 뒤 다시 재본 것

```
[고치기 전] req1: 500  ct=text/plain  body='Internal Server Error'
[고친 후 ] req1: 503  ct=application/json  Retry-After=5
           body='{"detail":"지금 요청이 몰려 있어. 잠시 후 다시 시도해줘."}'
```

> **🛠 전문가 노트** 이게 오늘 일곱 번 나온 모양이다 — **교훈을 배우면 배운 그 자리에 근거까지 적어두고, 같은 병이 있는 다른 입구는 안 쓴다.** 주석이 길고 정확할수록 오히려 '이건 해결됐다'는 착각이 강해진다.

## 5. 그리고 그 병을, 내가 그날 아침에 새로 심었다

검사가 내 당일 코드에서 결함 셋을 찾았다. 가장 아픈 것부터.

### 오탐 방지 장치가 오탐 생성기였다

아침에 만든 '서버를 태그로 찾는' 코드에, 실패했을 때 원인을 보여주려고 오류 메시지를 결과값과 **같은 통에 담았다.** 그러면 서버 조회가 **성공하면서** 경고 한 줄만 내도 —

▶ 실제 출력 — 재현

```
Name=blog-backend 인스턴스가 8개입니다: warning: urllib3 v2 only supports ... i-0abd...
  어느 쪽인지 스크립트가 정할 수 없습니다.
종료코드=1
```

경고 문장이 결과 목록에 섞여 단어 수가 늘고, "서버가 8개다"라며 멈춘다. **'여러 개면 위험하니 멈춘다'는 안전장치가 정확히 반대로 작동**했고, 이건 정지·배포·훈련·감시 다섯 스크립트의 공통 입구라 터지면 그날 아무것도 못 한다.

### 나머지 둘도 같은 계열

- **주석이 거짓이었다** — 저녁에 만든 디스크 감시에 "기동 직후엔 옛 형식이 올 수 있으니 폴백을 둔다"고 적었는데, 코드를 따라가보니 그 상황이 **일어날 수 없었다.** 도달 불가능한 코드였고, 게다가 기본값이 '문제 없음'이라 안전 방향도 반대였다
- **노출만 하고 기록은 안 했다** — 디스크 상태를 화면에는 내보내면서 저장은 안 해서, 감시가 두 번 도는 사이에 문제가 생겼다 사라지면 흔적이 0이었다. 창을 만들었는데 절반만 서 있었다

검사를 붙이는 손과 검사를 믿는 손이 같으면 이렇게 된다. **남이 봐주는 것의 값어치가 여기 있다** — 오늘은 그 '남'이 에이전트였다.

## 6. 저녁 — 보안검사에서 나온 두 가지

네 갈래(인증·인가 / 인젝션·SSRF·업로드 / 시크릿 / 인프라·IAM)를 돌렸다. 실제로 공격이 되는 건 둘이었고, **둘 다 내가 직접 재현했다.**

### ① 아무나 관리자 이름으로 댓글을 달 수 있었다

로그인한 사람이 댓글을 쓰면 이름을 서버가 정해준다. 그 자리 주석에 "남의 이름 사칭 방지"라고 적혀 있었다. 그런데 **로그인 안 한 사람은 이름을 직접 적는다.**

▶ 실제 출력 — 로그인 없이 실제로 해본 것

```
$ curl /api/blog-owner
{"id":1,"name":"<관리자 로컬파트>"}          ← 로그인 필요 없음
$ curl -X POST /api/posts/437/comments \
    -d '{"author":"<관리자 로컬파트>","content":"[재현] 공지: ..."}'
HTTP 201
{"author":"<관리자 로컬파트>", ...}          ← 진짜 관리자 댓글과 구분 불가
```

응답에 '회원이 쓴 것인지'를 가릴 정보가 **하나도 없었다.** 화면에서도 똑같이 보인다.

> **🔎 비유** 방명록에 이름을 손으로 적는 칸만 있는 것과 같다. 주인 이름을 그대로 적으면 주인이 쓴 글과 구별할 방법이 없다.

### 이름을 막는 쪽으로는 고치지 않았다

"그 이름은 못 쓰게 하자"가 첫 생각이었는데, 스스로 공격해보니 깨진다.

- **생김새가 같은 다른 글자**가 있다 — 키릴 문자 е는 라틴 e와 화면상 구별이 안 된다
- **보이지 않는 문자**를 끼우면 문자열은 다른데 화면은 같다
- "관리자님", "관리자 (운영)" 같은 변형은 완전일치 검사를 그냥 통과한다

**⚠️ 함정** — 그리고 결정타는 우회가 아니었다. "그 이름은 계정입니다"라고 거절하면 **로그인 없이 '이 이름의 계정이 있느냐'를 확인하는 창구**가 열린다. 막으려던 것보다 나쁜 걸 만드는 셈이다.

> **🛠 전문가 노트** 그래서 **보이는 이름은 그대로 두고, 사실을 따로 기록**했다 — 이 댓글이 어느 계정에서 왔는지를. 그리고 화면에는 '회원' 배지를 붙인다. 같은 이름을 쳐도 배지가 안 붙는다. 배지를 '회원' 쪽에 다는 게 중요하다 — '익명'에만 표를 달면 그 표가 빠지는 순간 사칭이 다시 통한다.

### ② 비공개 글이 몇 편인지가 새고 있었다

이 블로그는 글마다 공개 범위가 있다. 목록 API는 그걸 정확히 지킨다. 그런데 서버 상태 페이지의 '전체 글 수'는 **범위를 안 보고 다 셌다.**

▶ 실제 출력 — 공개 17 / 비공개 1 / 구독자전용 1 로 만들어놓고 로그인 없이

```
GET /api/posts?limit=1  → total 17
GET /api/status         → stats.posts 19      ← 차이 2 = 숨긴 글 수
```

내용은 안 샌다. 하지만 **'숨긴 글이 몇 편 있고 방금 하나 늘었다'**가 나간다. 덤으로 화면도 거짓말을 하고 있었다 — 상태 페이지는 19편이라는데 목록엔 17편만 있었다.

> **🛠 전문가 노트** 같은 파일 몇 줄 아래에 "이 응답은 로그인 없이 볼 수 있으니 수치를 그대로 내보내면 안 된다"는 판단이 이미 적혀 있었다. **그 기준이 바로 위 한 줄에는 적용돼 있지 않았다.** 오늘 일곱 번 나온 그 모양이다.

### 이메일이 화면으로 새던 경로를 뿌리째 끊었다

위 두 건의 재료가 같았다. 이 앱은 화면에 보일 이름이 필요할 때마다 **이메일 주소의 앞부분을 잘라 썼다.** 그 값이 로그인 없이 보이는 곳 두 군데로 나갔다.

가입이 초대제라 계정이 몇 개 없고 관리자는 **한 명뿐**이다. 메일 도메인은 공개 서비스라 앞부분만 알면 **주소 전체가 완성된다.** 가입 화면에서는 계정이 있는지 없는지도 안 알려주려고 애쓰는데, 정작 가장 중요한 계정 하나에 이름표를 붙여 내놓고 있었던 셈이다.

표시용 이름을 따로 두고, 이메일에서 만드는 코드를 **전부** 걷어냈다. 안 정하면 '회원'으로 뭉갠다 — **이메일로 되돌아가는 경로를 아예 없애는 게 요점**이다.

## 7. 인프라 — 알림을 끊을 수 있는 문이 열려 있었다

서버가 죽으면 메일을 보내는 알림 통로가 있다. 그 통로에 **접근 규칙을 안 적으면** 클라우드가 기본 규칙을 붙여주는데, 그 기본이 "이 계정 안에서는 누구나"였다.

이 저장소는 공개돼 있고, 자동 배포가 클라우드 권한을 잠깐 빌려 쓴다. 그러니 **그 배포 과정이 오염되면 알림 통로를 통째로 지울 수 있었다.**

▶ 실제 출력 — 권한 시뮬레이터로 전후 비교

```
[전] sns:Publish      → allowed  (Resource Policy)
     sns:DeleteTopic  → allowed  (Resource Policy)
[후] sns:Publish      → implicitDeny
     sns:DeleteTopic  → implicitDeny
     sns:ListSubscriptionsByTopic → allowed   ← 감시가 실제로 쓰는 것은 유지
```

> **🔎 비유** 경비 알람의 배선함에 잠금장치를 안 걸어둔 것과 같다. 알람 자체는 잘 작동하는데, 집에 드나드는 아무나 선을 뽑을 수 있다.

### 감시가 가장 중요한 계정을 안 보고 있었다

"공격자가 몰래 열쇠를 하나 더 만드는 것"을 감시하는 검사가 있었다. 그런데 감시 대상이 **이름으로 두 명만 적혀** 있었고, 실제 계정은 셋이었다.

빠진 하나가 하필 **관리자 권한 + 로그인 가능한 계정**이었다. 열쇠를 만들 가치가 가장 큰 계정이 검사 밖이었던 것이다. 게다가 이름을 적어두는 방식이라 **새 계정이 생겨도 안 보였다.**

> **🛠 전문가 노트** 이름을 코드에 안 적고 **전체를 훑도록** 바꿨다. 목록을 손으로 관리하지 않으면 목록이 낡지도 않는다 — 아침의 서버 ID 건과 완전히 같은 처방이다.

## 8. 배포 — 그리고 조용히 깨질 뻔한 것 하나

마이그레이션 3개와 '컨테이너를 관리자 권한으로 실행하지 않게' 하는 변경을 배포했다. 마지막 것이 위험 지점이었고, 실제로 걸렸다.

▶ 실제 출력 — 배포 직후 확인

```
uid=10001(appuser) gid=999(appuser)             ← 관리자 아님, 의도대로
touch /app/uploads/.wtest
  → Permission denied                            ← 업로드 폴더에 못 쓴다
```

서버 바깥 폴더를 컨테이너 안으로 연결해 쓰는데, 그 폴더의 주인이 예전 사용자라 새 사용자가 못 쓰게 된 것이다. 실제 업로드는 클라우드 저장소로 가기 때문에 **아무 증상 없이 지나갈 수도 있었다.**

**⚠️ 함정** — 이건 **재건할 때마다 반복될 자리**다. 그래서 고치고 끝내지 않고 복구 문서의 설치 절차에 한 줄을 넣었다. 안 넣으면 재해 복구 한복판에서 똑같이 겪는다 — 오늘 아침에 F5를 없앤 것과 같은 이유다.

▶ 실제 출력 — 고친 뒤

```
쓰기OK
touch /app/app/x → Permission denied            ← 앱 코드는 여전히 못 고친다(의도)
```

> **🛠 전문가 노트** 업로드 폴더만 권한을 열고 **앱 코드는 읽기만** 되게 남겼다. 프로그램이 자기 코드를 고칠 수 없게 하는 것이 요점이다.

## 9. 오늘 배운 것

어제 편이 "'안 한 일' 목록이 먼저 썩는다"였다. 오늘 나온 건 그 한 겹 아래다.

이 저장소는 문제를 겪으면 **그 자리에 이유를 길게 적는** 습관이 있다. 그건 좋은 습관이고, 실제로 오늘 검사가 잡은 것들의 근거를 대부분 그 주석에서 찾았다. 그런데 —

▶ 실제 출력 — 오늘 확인된 목록 (배운 자리 → 안 쓸린 입구)

```
botocore 기본 타임아웃이 위험하다   →  업로드 경로엔 그 설정이 없음
500 text/plain을 고쳤다              →  연결 부족은 그 처리에 안 걸림
메일 점검에 타임아웃을 건다          →  실제 발송엔 없음(무한 대기)
메일 실패가 조용히 삼켜진다(실측)    →  비번 재설정에 그대로 남음
'|| true'는 권한없음을 없음으로 만든다 →  훈련 스크립트가 그 패턴
이미지에 .env를 굽지 않는다           →  프론트 쪽엔 그 설정이 없음
읽기 전용 권한은 분리하는 게 낫다     →  정책만 갈리고 역할은 하나
남의 이름 사칭 방지                   →  고정이 로그인 쪽에만 걸림
로그인 없이 보는 응답엔 수치를 안 낸다 →  바로 위 한 줄은 전체를 셈
```

**하나 고치고 그 자리에 이유를 적는 것으로 끝내면, 그 이유가 오히려 '이건 해결됐다'는 착각을 만든다.** 배운 다음에 해야 할 일이 하나 더 있다 — 같은 병이 있는 **다른 입구를 찾아 쓰는 것.**

## 한 줄로 남기면

"고친 자리 옆에는 안 쓸린 입구가 있다. 교훈을 적어두는 것과 그 교훈을 전부 적용하는 것은 다른 일이고, 잘 적힌 주석일수록 그 차이를 가린다."

곁들임 — "검사를 안 한 것이 검사한 것처럼 읽히는 게, 검사가 실패하는 것보다 나쁘다. 실패는 신호를 내지만 침묵은 통과처럼 보인다."

하나 더 — "640KB를 어떻게 줄일지 이야기하는 동안 3MB가 지나가고 있었다. 논쟁하기 전에 재는 게 먼저다."

오늘의 아이러니 — "'기록이 현실보다 넓다'를 어제 고쳤는데, 오늘 아침 내가 쓴 코드에 그 병을 셋 심었다. 그중 하나는 **거짓 주석을 지적하는 커밋 안에 있던 거짓 주석**이었다."
