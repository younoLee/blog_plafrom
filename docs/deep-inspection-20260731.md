## 1. Content-Length만 보던 본문 상한 (07-30 발견 · 07-31 검증·고정)

### 무엇이었나

상한 검사가 `Content-Length` 헤더만 봤다. 그래서 같은 20MB를 헤더 없이 보내면 그냥 통과했다.
로컬 스택에 실제로 쏴서 재봤다:

```
A) Content-Length: 20000000  → 413  (0.012초)
B) Transfer-Encoding: chunked → 422  (7.7초, 20,002,488바이트가 전부 앱까지)
```

B가 우회다. 본문이 앱까지 들어와 메모리에 버퍼링된 뒤에야 JSON 파싱에서 튕겼다.
**로그인처럼 무인증으로 부를 수 있는 라우트에서도 된다.** t2.micro에서 이런 요청 몇 개면
메모리가 고갈된다.

앞단도 못 막는다 — CloudFront Function은 본문을 못 보고(같은 Content-Length 검사뿐),
WAF의 `SizeRestrictions_BODY`는 Count로 내려가 있다(그 규칙은 8KB 초과를 막는데
그러면 이미지 업로드가 죽으므로 되돌리는 게 답이 아니다). 방어는 앱에 있어야 했다.

### 고친 것

`BaseHTTPMiddleware` 대신 **순수 ASGI 미들웨어**로 바꿔 receive 채널을 직접 쥔다.
Content-Length가 있으면 한 바이트도 안 읽고 판정하고(가장 싼 경로), 없으면 상한까지만
버퍼링하며 세다가 넘는 순간 앱을 부르지 않고 끊는다.

### 07-31에 검증한 것

수정 후 같은 두 발을 다시 쐈다:

```
A) Content-Length  → 413  (0.012초)
B) chunked         → 413  (0.098초)   ← 7.7초 → 0.098초
```

그리고 **더 중요한 것**을 쟀다. 이 수정의 진짜 위험은 우회가 아니라 **정상 요청을 조용히
망가뜨리는 것**이다(읽어버린 본문을 앱에 되돌려주지 못하면 모든 POST가 깨진다).

```
chunked 정상 JSON 로그인 → 401   (Content-Length 대조군과 동일)
chunked 5MB(상한 이하)   → 422   (본문이 끝까지 도착해 파서까지 감)
```

### 회귀 테스트 7개 (`tests/test_body_limit.py`)

HTTP 레벨은 TestClient가 본문을 한 덩어리로 합쳐 넘기므로 조각 경계를 재현하지 못한다.
그래서 스트리밍 동작은 미들웨어를 **ASGI 레벨에서 직접 호출**해 검증했다.

| 테스트 | 무엇을 못박나 | 수정 전 |
|---|---|---|
| `test_chunked_body_over_limit_is_blocked` | 우회 차단 | **실패 (422)** |
| `test_content_length_body_over_limit_is_blocked` | 기존 경로 안 깨짐 | 통과(대조군) |
| `test_chunked_body_under_limit_reaches_app_intact` | replay 무결성 | 통과(계약 고정) |

## 4. BYOK 자격증명 복호화 실패가 500 text/plain (07-31 발견·수정)

`LLM_ENCRYPTION_KEY`가 바뀌면(로테이션·환경 불일치) 저장된 암호문을 못 푼다. 그때
Fernet의 `InvalidToken`이 **아무데서도 안 잡히고 있었다** — `_load_byok_credential`은
`BYOKNotConfiguredError`만 잡고, 호출 위치는 `create_draft`의 try 블록 **밖**이다.

실측(예전 키로 저장 → 서버 키 교체 → 초안 요청):

```
cryptography.fernet.InvalidToken   → 500 Internal Server Error (text/plain)
```

**07-28 카오스 훈련에서 DB(→503)·S3(→503)에 대해 고친 것과 같은 병이 BYOK 경로에만
남아 있었다.** 프론트는 JSON을 기대하므로 파싱조차 못 하고, `isAsleepStatus`(502/503/504)의
안내 경로도 안 탄다. 사용자는 '서버가 터졌다'만 보고, 정작 자기가 할 수 있는 일
(키 재등록)은 알 길이 없다.

고친 것: `llm_keys`에 `CredentialUndecryptableError`를 두고 라우터가 **503 + 재등록 안내**로
변환한다. 타입을 나눈 이유는 '설정 안 됨'과 '풀 수 없음'이 사용자가 할 일이 다르기 때문이다
(앞은 서버 설정, 뒤는 키 재등록). 회귀 테스트 1개.

## 5. 알림 배지가 목록과 다른 기준을 보고 있었다 (07-31 발견·수정)

알림 **목록**에는 가시성 조건(`visible_condition`)이 걸려 있었는데 — 주석에 "글이 private로
바뀌면 제목이 새던 것"을 고쳤다고 적혀 있다 — **unread 카운트에는 없었다.**

실측: 구독 중인 글쓴이가 글을 private로 내리면

```
items  = []      (목록은 비었다)
unread = 1       (배지는 1)
```

사용자는 **눌러도 사라지지 않는 배지**를 본다. 한쪽만 고쳐진 전형적인 모양이다.
조건을 한 번만 만들어 두 쿼리가 같은 것을 쓰게 했다(구독 조회 쿼리도 하나 아낀다).
회귀 테스트 1개 — 수정 전 `assert 1 == 0`으로 실패하는 것 확인.

## 6. SDK에 넘긴 httpx 클라이언트를 안 닫고 있었다 (07-31 · 위생 수정)

BYOK `compatible` 경로는 리다이렉트 추종을 끄려고 `httpx.Client`를 직접 만들어 OpenAI SDK에
넘긴다. 그런데 SDK는 넘겨받은 `http_client`의 수명을 책임지지 않으므로 커넥션 풀이 GC
시점까지 남는다. `finally`에서 닫게 했다.

하드 누수는 아니다(GC가 결국 정리한다). 다만 하필 이 경로는 **호스트를 사용자가 정하는
유일한 곳**이고 t2.micro라, 명시적으로 닫는 게 맞다.

## 8. 안 고친 것 (기록)

- **413·403 응답에 CORS 헤더가 없다.** 미들웨어 순서가 `origin_secret → 본문상한 → CORS`라
  앞의 둘이 낸 응답은 CORS를 안 거친다. 운영은 CloudFront가 프론트·API를 같은 오리진으로
  서빙해 무관하고, **로컬 개발(:5173 → :8000)에서만** 브라우저가 413 대신 네트워크 오류로
  본다. 순서를 바꾸면 CORS 프리플라이트가 시크릿 검사보다 먼저 답하게 되므로 트레이드오프다.
  지금 순서가 의도된 것이라 그대로 둔다.
- **복호화 실패 시 시간당 '시도' 슬롯이 반환되지 않는다.** `_reserve_abuse_slot`이
  `_load_byok_credential`보다 먼저 돌기 때문이다. 서버 쪽 사고로 사용자가 한도를 하나 잃는다.
  다만 "시도 캡은 실패도 센다"가 의도된 계약이고, 이 상태(키 교체)에서는 BYOK 기능 자체가
  이미 망가져 있다. 계약을 곁다리로 바꾸는 게 더 나쁘다고 판단해 기록만 한다.
- **업로드 상한이 IP 기준이다.** (2번 참고)
- **`_reserve_abuse_slot`의 고정 창(fixed window)** — 07-30 문서의 판단 그대로.
