## 찾은 결함 5건

### F1 — 1단계 `terraform apply`가 즉시 실패 (블로커)

```
Error: No value for required variable
  on ecs.tf line 9: variable "backend_image_tag"
```

07-24 ECS 이전이 기본값 없는 필수 변수를 추가했다. ECS는 그날 tear down했지만 변수는 남았고,
**아무도 DR 경로를 다시 밟지 않아서** 재해 복구의 첫 명령이 죽는 상태로 3일이 지났다.

*수정:* `backend_image_tag`에 기본값 `""`를 주고, 빈 값 검사는 실제로 태스크를 만드는
자리(`aws_ecs_task_definition`의 `precondition`)로 옮겼다. 위험한 곳에서만 시끄럽게 실패한다.

### F2 — 그걸 넘겨도 tear down한 ECS 스택이 부활 (비용·폭발반경)

더미 태그를 넣고 plan을 떠보니 `Plan: 10 to add` — `aws_db_instance`, `aws_lb`,
`aws_ecs_service(desired_count=2)`, 오토스케일링까지. 07-24에 일부러 없앤 월 $50~70짜리
인프라가 **EC2 하나 살리려는 apply에 딸려 살아난다.** 게다가 이미지 태그가 가짜라
태스크는 `CannotPullContainerError`로 안 뜨고, 사고 한복판에 노이즈만 남긴다.

*수정:* `enable_ecs`(기본 `false`)로 해당 10개를 게이트했다. state에 없는 리소스들이라
count 추가가 state 이동을 일으키지 않는 것을 먼저 확인하고 손댔다.
**검증:** 인자 없는 `terraform plan`이 이제 `without changing any real infrastructure`.

### F3 — 새 인스턴스를 찾는 명령이 아무것도 못 찾는다 (RTO의 절반을 먹은 범인)

`ec2.tf`의 태그가 `Name = "blog-backend "` — **끝에 공백**이 있었다(콘솔에서 만든 값을
그대로 맞춘 것). 런북의 조회 명령은 AWS CLI 축약 필터를 쓴다:

```bash
--filters "Name=tag:Name,Values=blog-backend "     # → 아무것도 안 나옴
```

축약 파서가 값 뒤 공백을 잘라내기 때문에 매칭이 안 된다. 공백을 뺀 필터도 실제 태그와
달라서 역시 안 된다. **JSON 형식 필터로만 매칭된다** — 사고 중에 그걸 떠올릴 이유가 없다.
결과는 `IID=None` → 다음 줄이 `InvalidInstanceID.Malformed`로 사망.

*수정:* 태그에서 공백을 제거하고(`ec2.tf`, in-place 갱신) 축약 필터가 동작하는 것을 확인했다.
런북에는 `IID`가 비면 즉시 멈추는 가드와 "빈 값이면 태그부터 의심하라"는 주석을 넣었다.

### F4 — "alembic은 no-op"이라는 단언이 틀렸다

런북 7단계는 `(alembic은 이미 head라 no-op이 된다)`라고 못 박아 뒀다. 실제 로그:

```
Running upgrade b7f1c4e29a03 -> c1d2e3f4a5b6, add index on posts.created_at (정렬 핫패스)
```

백업은 07-22 시점(`b7f1c4e29a03`)이고 head는 07-24 이후(`c1d2e3f4a5b6`)다. 이번엔 인덱스
하나라 무해했지만, **백업이 오래될수록 이 자리에서 진짜 DDL이 돈다.** 실패하면 백엔드가
아예 안 뜨는데, "no-op일 텐데"라고 적혀 있으면 원인을 여기서 찾지 않게 된다.

*수정:* 문구를 "여기서 실제로 마이그레이션이 돈다, 로그에서 확인하라"로 바꾸고
확인 명령을 붙였다.

### F5 — 인스턴스 ID를 갈아끼울 파일 목록이 불완전

런북은 3개(`stop_server.sh`·`restore_drill.sh`·`env_escrow.sh`)를 적었는데 실제로는 **5개**다.
빠진 건 `watch.sh`와 `deploy_backend.sh`.

`watch.sh`가 특히 나쁘다 — 감시 스크립트가 **존재하지 않는 인스턴스를 계속 들여다보게**
된다. 이 저장소가 반복해서 당하는 병("설정했다 ≠ 동작한다")의 전형이고, `deploy_backend.sh`는
07-22 shellcheck 목록에서도 똑같이 누락됐던 파일이다. 목록을 손으로 유지하면 새로 생긴
파일이 첫날부터 검사 밖에 있게 된다.

*수정:* 목록을 5개로 고치고, 손 유지가 필요 없는 일괄 치환을 런북에 넣었다:
`sed -i "s/^INSTANCE_ID=.*/INSTANCE_ID=$IID/" scripts/*.sh`

## 남은 개선 후보

- **EIP가 없어 재건마다 DNS가 바뀐다.** 그래서 8단계(오리진 전환)와 스크립트 ID 갱신이
  매번 필요하다. EIP를 붙이면 이 두 단계가 통째로 사라지지만, 정지 중 EIP는 과금된다
  — "상시 $0" 원칙과 맞바꿀지 판단 필요.
- **인스턴스 ID 하드코딩 자체를 없애기.** 5개 스크립트가 태그 조회로 ID를 찾게 하면
  F5는 구조적으로 재발하지 않는다. (F3을 고쳐 태그 조회가 이제 신뢰 가능해졌다)
- **user_data 부트스트랩.** 2단계를 손으로 하는 대신 인스턴스가 스스로 깔게 하면
  재건이 짧아지고 "AMI는 맨바닥"이라는 함정도 사라진다.
