## 1. 실제 공격 가능했던 것 — 2건, 둘 다 재현하고 닫았다

### ① 익명 댓글로 블로그 주인 사칭

```
GET  /api/blog-owner            → {"name":"<관리자 로컬파트>"}   ← 무인증
POST /api/posts/{id}/comments   {"author":"<그 이름>", ...}      → 201
GET  /api/posts/{id}/comments   → 회원 댓글과 구분 불가
```

로그인 사용자는 작성자명이 서버 값으로 고정되는데 **익명만 자유 입력**이었다.
그 자리 주석에는 "남의 이름 사칭 방지"라고 적혀 있었다 — 방지가 로그인 쪽에만
걸려 있었던 것이다. 응답 스키마에 회원/익명을 가를 필드가 **하나도 없었다.**

**이름을 검사하는 쪽으로 고치지 않았다.** 자기공격해보니 깨진다:

| 우회 | 결과 |
|---|---|
| 동형문자 `еs…` (Cyrillic е U+0435) | 육안 동일, 모든 ASCII 비교 통과 |
| 제로폭/NBSP `es…​` | `strip()`이 못 잡고 렌더링 동일 |
| 접미 `es…님`, `es… (관리자)` | 완전일치 통과. 부분일치로 바꾸면 정상 이름 과차단 |

그리고 결정타는 우회가 아니다 — **"그 이름은 계정이다"를 400으로 알려주면 무인증
계정 열거 오라클이 된다.** 로그인 없이 시간당 20번씩 확정적으로 물어볼 수 있다.
고치려던 것보다 나쁜 걸 만든다.

→ 표시값은 그대로 두고 **사실을 따로 기록**한다. `comments.user_id`(NULL = 익명) +
응답의 `is_member` 1비트 + 프론트 배지. 같은 이름을 쳐도 회원으로는 안 보인다.
배지를 '회원' 쪽에 다는 방향이 중요하다 — 반대로 '익명'에만 표를 달면 그 표가
빠지는 순간 사칭이 다시 통한다(fail-open).

### ② 비공개 글의 개수가 무인증으로 샜다

```
공개 17 / 비공개 1 / 구독자전용 1 일 때
무인증 GET /api/posts?limit=1 → total 17
무인증 GET /api/status        → stats.posts 19      ← 차이 2 = 숨긴 글 수
```

앱의 모든 독자 경로가 `visible_condition`을 지키는데 **이 집계 하나만** 빠져 있었다.
내용은 안 새지만 존재·개수·증가 시점이 나간다(캐시 때문에 최대 60초 지연 관측).

같은 파일 몇 줄 아래 `disk_ok`가 *"무인증 공개라 수치는 공격 진척 계기판이 된다 →
1비트만"* 이라고 판단해놓고, 그 기준이 이 줄에는 적용돼 있지 않았다.
→ `where visibility = 'public'`. 덤으로 UI 거짓말도 닫혔다 — 상태 페이지가 19라
말하는데 목록은 17만 보여주던 상태였다.

`subscribers` 카운트는 **그대로 뒀다.** 기준은 '시행 중인 통제를 우회하는가'인데,
`author_subscriptions`에는 행 단위 가시성 개념이 없다(비공개 구독이라는 게 없다).
우회할 통제가 존재하지 않는 순수 공개 집계다.

## 2. 정보 노출 — 이메일이 화면으로 새는 경로를 뿌리째 끊었다

이 앱은 화면에 보일 이름이 필요할 때마다 **이메일에서 유도**했다(`email.split("@")[0]`).
그 값이 무인증 경로 둘로 나갔다:

- `GET /api/blog-owner` — 관리자 로컬파트를 무인증·무제한으로 반환
- 공개 글의 댓글 목록 — 회원 댓글의 작성자명으로 **영구 저장·공개**

가입이 초대제라 계정이 희소하고 **admin은 단 하나**다. 발신 도메인이 공개 제공자임이
설정 주석에 적혀 있어, 로컬파트만 알면 **전체 주소가 완성된다.** `register`가 애써 막은
계정 열거를 가장 값나가는 계정에서 무효화하고 있었다. 그리고 그 값이 위 ①의 재료였다.

→ `users.display_name`(nullable)을 도입하고 유도를 **전부** 걷어냈다(인증 뒤 경로
4곳 포함). NULL이면 `"회원"` / 블로그 기본 제목으로 뭉갠다 — **이메일로 되돌아가는
경로를 아예 두지 않는 게 요점이다.**

```bash
# 이름을 보이고 싶으면 (안 정하면 '회원'으로 보인다)
docker compose exec backend python scripts/create_user.py you@x.com \
  --update-if-exists --display-name '유노'
```

유도를 한 군데라도 남기면 "이름은 이메일에서 만든다"는 관습이 살아남고, 그게 무인증
경로로 다시 새어나간 것이 이번 건이다.

## 3. 인프라 — 시뮬레이터로 실증하고 닫은 것

### SNS 토픽이 계정 내 모든 주체에게 열려 있었다

`aws_sns_topic`에 `policy`를 안 주면 AWS가 기본 정책을 붙인다. 라이브 값:

```
Principal: {"AWS": "*"}   Condition: AWS:SourceOwner = 이 계정
Action: Publish · DeleteTopic · Subscribe · AddPermission · …
```

같은 계정 안에서는 신원 정책 **또는** 리소스 정책 중 하나만 허용해도 통과한다.
즉 **공개 저장소의 Actions가 OIDC로 맡는 배포 역할이 알림 토픽을 지울 수 있었다.**
토픽이 지워지면 EC2 상태검사 알람이 죽은 ARN을 가리킨 채 조용히 아무에게도 안 간다.

이건 `iam-github-oidc.tf`가 정확히 반대로 추론한 자리다 — 거기서 감시 역할의
`ListSubscriptionsByTopic`을 토픽 하나로 좁힌 이유가 "오염된 액션이 구독 주소를 읽는
것"이었는데, **같은 액션이 그 토픽을 통째로 지울 수 있었다.** 폭발 반경을 신원 정책
쪽에서만 쟀다.

`simulate-principal-policy` 전후:

| 액션 | 전 | 후 |
|---|---|---|
| `sns:Publish` | **allowed (Resource Policy)** | `implicitDeny` |
| `sns:DeleteTopic` | **allowed (Resource Policy)** | `implicitDeny` |
| `sns:ListSubscriptionsByTopic` | allowed | allowed (감시가 실제로 쓴다) |

→ `aws_sns_topic_policy`를 명시해 Principal을 **CloudWatch 서비스 주체**(SourceArn으로
이 계정 알람만) + **계정 루트**로 좁혔다. 계정 루트에 위임하면 "누가 할 수 있나"가
`iam-*.tf` 한 곳에서만 결정된다 — 리소스 정책이 신원 정책을 우회하던 구조를 없앤다.

### 감시가 AdministratorAccess 사용자 하나를 통째로 빠뜨렸다

라이브 IAM 사용자는 3명인데 감시 루프는 **2명만** 하드코딩돼 있었다. 빠진 `youno`는
**AdministratorAccess + 콘솔 로그인**이 있는 계정이다. 이 검사가 선언한 위협모델이
"공격자가 지속성 확보하려고 키를 추가한다"인데, **키를 만들 가치가 가장 큰 계정**이
루프 밖이었다. 게다가 하드코딩이라 **새 IAM 사용자 생성 자체가 안 보였다.**

→ `iam:ListUsers`를 주고 **열거 기반**으로 바꿨다. 사용자 이름을 코드에 안 박으면
목록이 낡지 않는다. 키 0개(콘솔 전용)를 정상으로 처리하는 분기도 함께 넣었다 —
열거로 바꾸면서 새로 생긴 경로이고, 안 넣으면 "생성일을 못 읽었다"는 가짜 실패가 난다.

실행 결과: `✅ youno 액세스키 0개 (콘솔 전용 — 장기 키 없음)`

### 감시 역할이 배포 역할이었다

`iam-github-oidc.tf`의 주석은 *"관심사가 다르니 읽기 전용은 분리해 두는 편이 낫다"*고
적어놓고, 실제로 갈린 건 **정책 문서뿐이고 역할은 하나**였다. 매시 도는 감시 잡이
사이트 버킷 Put/Delete + CloudFront 무효화 권한을 함께 쥐고 돌았다.

→ `github-actions-blog-watch` 전용 역할 신설(트러스트는 동일: 이 저장소 main만).
검증: 새 역할은 `DescribeInstances`·`ListUsers`·버킷 `ListBucket` **allowed**,
`PutObject`·`DeleteObject`·`CreateInvalidation` **implicitDeny**. 배포 역할은 실제
버킷/키에 대해 그대로 allowed(배포 안 깨짐을 별도 확인).

### 계정 수준 방어 둘

- **EBS 기본 암호화** `False` → `True`. pgdata(비밀번호 해시·BYOK 암호문)가 평문
  at rest였다. S3 백업 3종은 전부 SSE-AES256인데 원본만 아니었다. 무료이고, **재해
  복구로 새 볼륨을 만들면 자동 적용된다**(기존 볼륨 소급은 안 된다).
- **계정 수준 S3 퍼블릭 액세스 차단** 미설정 → 4종 전부 true. 기존 4개 버킷은 이미
  개별 차단이라 무영향이고(적용 후 사이트 200 확인), 앞으로 만드는 버킷이 보호된다.

## 4. 그 밖에 닫은 것

- **`base_url` 포트가 500 text/plain을 냈다.** `urlparse().port`는 파싱이 아니라
  **속성을 읽는 순간** `ValueError`를 던진다. 라우터가 자체 예외만 잡아 그대로 샜다 —
  07-28·07-31에 DB·S3·BYOK에 대해 반복해서 고친 병이 이 입구에만 남아 있었다.
- **`frontend/.dockerignore`에 `.env*`가 없었다.** 백엔드는 정확히 이 구멍으로 사고를
  내고 막아뒀는데 프론트만 예외였다. 최종 이미지엔 안 남지만 **build 스테이지
  레이어에는 남는다.**
- **컨테이너가 root로 돌았다.** `useradd --uid 10001` + `USER appuser`. uploads만
  소유권을 넘기고 앱 코드는 root 소유로 남겨 **프로세스가 자기 코드를 못 고치게** 했다.
  실측: `touch /app/app/x` → `Permission denied`.
- **결제 안전장치가 기동 가드를 못 받고 있었다.** `PAYMENTS_REQUIRE_LIVE`의 코드
  기본값이 False이고 시크릿키 기본값이 **실제 토스 테스트 키**라, `.env` 한 줄이 빠지면
  검사가 통째로 사라진 채 테스트 결제가 Pro로 붙는다. `SECRET_KEY`·`S3_BUCKET`에는
  이미 같은 모양을 막아뒀는데 결제만 빠져 있었다. 회귀 경로가 가설이 아니다 —
  `env_escrow`/DR로 `.env`를 재조립하는 절차가 실재한다.
  (키 종류는 기동 때 안 본다. 현행 운영이 바로 `require_live=true` + 테스트 키 =
  의도적 결제 차단 상태라, 키까지 막으면 멀쩡한 서버가 기동을 거부한다.)
- **런북이 재해 중에 없는 증상을 찾게 만들었다.** "403이 200+HTML로 보인다"는 서술이
  세 곳에 남아 있었는데 그 블록은 07-28에 제거됐다(라이브 `CustomErrorResponses.Quantity=0`
  실측). 같은 저장소의 `watch.sh`는 반대로 403을 곧바로 그 원인으로 안내한다 —
  두 문서가 정면 모순인 채였다. 07-27 게임데이가 "RTO 42분 중 20분이 문서가 틀린
  자리"라고 결론 낸 그 부류다.

## 5. 깨끗했던 것 — 결과의 절반은 이쪽이다

취약점 목록만 남기면 이 시스템이 실제보다 나빠 보인다. 확인하고 문제없던 것:

- **SQL 인젝션 0건.** `text()` 사용처 7곳 전부 사용자 입력이 안 들어간다. 검색은
  `_like_escape` + `ESCAPE`. 실측 4케이스(`%%%%`, `a%_b`, `'; drop table posts;--`, `\`)
  전부 리터럴 처리.
- **XSS 싱크 0건.** `dangerouslySetInnerHTML`·`innerHTML`·`rehype-raw` 전부 없음.
  `react-markdown`의 기본 `urlTransform`이 `javascript:`를 무력화. CSP는 report-only가
  아니라 **enforce**(라이브 응답 실측).
- **SSRF 15케이스 전부 차단** — IMDS·IPv4-mapped IPv6·십진수/8진수/16진수 IP·
  loopback·평문 http. IMDSv2 강제(`http_tokens=required`)와 `follow_redirects=False`도
  주석 설명대로 실재.
- **업로드 우회 4종 방어** — 경로조작(파일명 완전 폐기)·SVG polyglot(400)·
  Content-Length 위조(413)·**chunked 12MB(6.3MB에서 413)**. 07-30에 발견된 chunked
  우회가 실제로 닫혀 있다.
- **히스토리에 시크릿 0건** — 257커밋 + 커밋된 docx 27개 내부까지. `.gitleaks.toml`
  예외 8개 전부 앵커가 붙어 있고 근거가 적혀 있다.
- **OIDC 신뢰조건에 와일드카드 0.** fork PR 탈취 불가(2중: `ci.yml`에 `id-token: write`가
  없고, 설령 있어도 `sub`가 `:pull_request`라 안 맞는다). 액션 SHA 핀 100%.
- **IAM 콘솔 드리프트 0건.** 역할 5개의 신뢰·인라인·연결 정책이 terraform과 일치.
- **BYOK 평문 유출 경로 0건.** `get_credential` 호출자가 단 하나이고 반환값이 응답·
  로그·예외 어디에도 안 실린다.
- **인증·인가의 뼈대가 튼튼하다** — JWT `algorithms=["HS256"]` 리스트 명시, **role을
  토큰에 안 담고 매 요청 DB에서 읽음**(승인·강등·차단이 즉시 반영), ban은
  `token_version`으로 즉시 무효화(4중), 결제는 금액을 서버가 정하고 `with_for_update()`로
  직렬화, IDOR 소유자 조건이 전 라우터에 걸려 있음.

## 6. 에이전트가 스스로 철회·강등한 것

검사의 값어치는 찾은 것만큼 **취소한 것**에도 있다.

- **`/auth/verify` 취약점 — 철회.** 토큰 발급처가 `register()` 안 두 곳뿐인데 그 함수는
  `allow_signup=False`로 첫머리에서 403이다. **도달 불가능한 코드**였다.
  "코드가 존재한다"를 "도달 가능하다"로 센 것.
- **토스 테스트키 — 닫힘(확인).** 운영 `.env`에 `PAYMENTS_REQUIRE_LIVE=true`가 있어
  요청 시점 503. 다만 구조적 지점(위 §4의 기동 가드)은 살아 있어 그건 고쳤다.
- **가시성 누출의 관측 입도 정정.** `/api/status`는 60초 캐시라 "30초 간격 폴링"은
  틀렸다. 결론은 안 바뀌지만 근거 문장은 정확해야 한다.
- **검사 지시서의 전제 정정.** 내가 "`gen-static.mjs`가 DB 본문을 HTML로 굽는다,
  거기가 제일 유력하다"고 지시했는데 **틀렸다** — 입력은 `content/devlog/*.md`이고
  커밋 권한이 있어야 바꿀 수 있다. 사용자 입력 경로가 아니다.
