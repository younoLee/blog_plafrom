# 카오스 훈련 — 의존성 장애 주입 (2026-07-28)

DR 게임데이(07-27)·IR 훈련(07-27)에 이은 세 번째 훈련. 이번 질문은 하나다:

> **바깥이 죽으면 우리 앱은 어떻게 죽는가.** 우아하게 안내하고 물러나는가, 아니면 500으로 터지는가.

이 프로젝트는 EC2 한 대 위에 앱과 DB가 같이 있고, 밖으로는 Anthropic·SMTP·S3에 의존한다.
평소엔 다 살아 있으니 '죽었을 때의 코드'는 **한 번도 실행되지 않는다.** 그래서 일부러 죽였다.

## 어떻게 했나

개발 스택이 이미 8000·5432·1025를 쓰고 있어서, 포트를 겹치지 않는 **격리 스택**을 따로 띄웠다
(`docker compose -p chaos` + 포트 오버라이드). 훈련이 남의 작업 환경을 죽이면 안 된다.

주입 전에 **정상 기준선**을 먼저 찍었다. 비교 대상이 없으면 "원래 그랬던 것"과 구분이 안 된다.

프로브는 사용자가 실제로 밟는 경로 7개: 헬스체크 · 서비스 상태 · 글 목록(비로그인) · 내 정보 ·
글 작성 · AI 초안 · 로그인.

## 결과 — 주입 4건

### ① DB 정지 (`docker stop chaos-db-1`)

| | 훈련 전 | 고친 뒤 |
|---|---|---|
| 글 목록·로그인·내 정보·글 작성 | `500` `text/plain` "Internal Server Error" | `503` `application/json` + `Retry-After: 30` |

**왜 500이 나쁜가.** 프론트(`api/http.ts`)의 `isAsleepStatus`는 **502/503/504만** '일시적 장애'로
안내한다. 500은 그 경로를 안 타서 사용자는 그냥 빨간 에러를 본다. 게다가 `text/plain`이라
`res.json()`이 파싱조차 못 한다. 500은 "이 요청이 잘못됐다"로 읽히지만 실제 상황은
"지금 서버가 못 한다"다 — 코드가 상황을 잘못 말하고 있었다.

**잘 되어 있던 것:** 백엔드는 크래시하지도 재시작하지도 않았다(`restarts=0`). 스택트레이스는
로그에만 남고 응답으로 새지 않았다. `/api/status`는 최대 60초 뒤 `database: down`으로 뒤집혀
`watch.sh`가 잡을 수 있는 상태가 됐다.

**의도적으로 안 바꾼 것:** `/api/health`는 DB 장애 중에도 200이다. 헬스체크가 DB를 보면
DB가 죽었을 때 컨테이너가 재시작 루프에 빠지는데, 재시작은 DB를 되살리지 못한다.
liveness는 200으로 두고 '무엇이 죽었나'는 `/api/status`가 말하는 분담이 맞다.

### ② 메일(SMTP) 정지

비밀번호 재설정 요청이 `202 "재설정 링크를 보냈어"`를 그대로 반환했다. 메일은 안 갔다.

**이건 고치지 않았다.** 계정 존재 여부를 숨기려면 성공/실패를 구분해 알려주면 안 된다
(가입된 주소든 아니든 같은 응답이어야 한다). 대신 확인한 것: 실패가 로그에 트레이스백으로
남고, `/api/status`의 `mail`이 60초 안에 `down`으로 뒤집혀 **감시가 잡는다.**
사용자에게 못 알려주는 대신 운영자는 안다 — 이 조합이면 받아들일 만하다.

### ③ AI 업스트림 (Anthropic)

두 가지를 갈라서 주입했다. **'거부'와 '무응답'은 다른 사고다.**

| 상황 | 훈련 전 | 고친 뒤 |
|---|---|---|
| 연결 거부 | 0.5초 → `502` "키/모델명 확인" | 0.5초 → `503` "일시적으로 연결할 수 없어" |
| 연결은 받고 무응답 | **115초** → `502` "키/모델명 확인" | **52초** → `503` "일시적으로 연결할 수 없어" |
| 잘못된 키 | `502` "키/모델명 확인" | `502` "키/모델명 확인" (그대로) |

**115초가 왜 문제인가.** 타임아웃 60초 × 재시도 1회다. 그런데 CloudFront의 오리진 read
timeout이 60초라, **사용자는 이미 504를 본 뒤인데 백엔드 워커는 55초를 더 붙잡혀 있다.**
아무도 볼 수 없는 응답을 위해 t2.micro의 용량을 태우는 셈이다.

**타임아웃을 줄여 재시도를 살리는 선택은 안 했다.** `cloudfront.tf` 주석에 기록된 대로
정상 초안이 30초를 넘긴 적이 실제로 있다(그래서 오리진 타임아웃을 60초로 올렸다).
25초씩 2회로 쪼개면 그 정상 요청이 죽는다. 예산이 60초 하나뿐이면 느리지만 성공할
한 번에 다 주는 게 낫다 → **타임아웃 55초 · 재시도 0회.**

**훈련이 아니었으면 놓쳤을 것:** 문구를 고치려고 `except httpx.TimeoutException`을 걸었는데
**하나도 안 걸렸다.** 벤더 SDK가 httpx 예외를 자기 타입으로 감싸기 때문이다. 재주입해서
52초를 기다린 끝에 여전히 "키/모델명 확인"이 나오는 걸 보고 알았다. 지금은 예외 원인
사슬(`__cause__`/`__context__`)을 훑어 판정한다.

### ④ S3 장애 (없는 버킷 + 잘못된 자격증명)

이미지 업로드가 `500` `text/plain`으로 터졌다. `s3.put_object`에 예외 처리가 아예 없었다.
→ `503` + "이미지 저장소에 일시적으로 접근할 수 없어". 버킷명·권한 오류 같은 내부 사정은
로그에만 남긴다.

## 곁다리로 나온 것

`/api/status`의 `checked_at`이 **호출 시각**을 새로 찍고 있었다. 실제 점검은 최대 60초 전
것인데 방금 잰 것처럼 보인다. 사고 중에 "방금 확인했는데 ok라는데?"로 사람을 헷갈리게 하는
종류의 거짓이라, 점검이 실제로 돈 시각을 그대로 내보내게 고쳤다.

## 숫자

- 주입 4건 · 프로브 경로 7개 · 크래시 0회 · 재시작 0회
- `500 text/plain` 응답: **6종류 → 0**
- 멈춘 업스트림에서 워커 점유: **115초 → 52초** (CloudFront 예산 60초 이내)
- 회귀 테스트 8개 추가 — 전부 **고치기 전 코드에서 실패하는 것까지 확인**

## 배운 것

**"죽었을 때의 코드"는 평소에 한 번도 안 돌아서, 있는지 없는지도 모른다.**
S3 예외 처리는 아예 없었고 아무도 몰랐다. 프로덕션에서 S3가 처음 흔들리는 날 알게 됐을 것이다.

**상태코드는 사용자에게 보내는 문장이다.** 500과 503의 차이는 숫자 3이 아니라
"네가 뭘 잘못했다"와 "내가 지금 못 한다"의 차이고, 이 앱에선 그게 프론트의 안내 분기까지 바꾼다.

**고쳤다고 생각한 것이 안 고쳐졌을 수 있다.** 예외 타입만 보고 잡은 문구 수정이 실제로는
한 번도 발동하지 않았다. 주입을 다시 하지 않았으면 "고쳤다"고 적고 넘어갔을 것이다.
**훈련의 값은 주입이 아니라 재주입에 있다.**

## 남은 것 (안 고침)

- **메일 실패를 사용자에게 안 알림** — 계정 열거 방어와의 맞교환. 감시가 잡는 것으로 갈음.
- **`/api/health`가 DB를 안 봄** — liveness/readiness 분리는 ECS로 갈 때 다시 볼 것.
  지금 EC2 한 대 구성에선 재시작 루프만 만든다.
- **BYOK compatible 경로** — 사용자가 base_url을 직접 정하는 유일한 경로라 이미 20초로
  따로 짧게 잡혀 있다(`COMPATIBLE_TIMEOUT`). 이번 훈련에서 별도로 안 건드렸다.
