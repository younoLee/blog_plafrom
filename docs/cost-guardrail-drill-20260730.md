## 어떻게 했나

실제 Anthropic 호출이 일어나는 훈련이라(통과한 요청 수 = 실제 청구 건수) 프로덕션을 때리지 않고
**로컬 스택**에 같은 코드로 붙였다. 캡은 프로덕션과 동일한 기본값(`config.py`: 시간당 10 · 일일 20 ·
월간 200 — 서버 `.env`에 `AI_*`가 없어 기본값이 그대로 프로덕션 값이다).

시나리오는 **경계에 세워놓고 밀기**다. "오늘 이미 19/20을 썼다. 남은 건 1회다"를 DB에 만들어 놓고
동시 요청 5발을 던진다. 캡이 총량을 묶는다면 성공은 정확히 1건이어야 한다.
모델은 가장 싼 하이쿠, 메모는 한 줄이다.

## ① 일일·월간 캡이 동시 요청을 못 막았다 (수정함)

```
════ 동시 요청 5개 발사 (남은 한도는 1회) ════
  req code  elapsed(s)
  1 200 1.62
  2 200 2.00
  3 200 2.96
  4 200 1.98
  5 200 1.91
  전체 벽시계: 2.98s

  200(실제 Anthropic 청구): 5건   429(차단): 0건
  ai_usage(일일).count   = 24   ← 캡 20
  일일 캡 초과분          = 4건  ❌ 캡이 청구를 묶지 못했다
```

**5건 전부 통과했다.** 남은 한도가 1회인데 24/20이 됐다 — 20% 초과 청구.

### 왜

07-24에 시간당 캡의 같은 결함(TOCTOU)을 고쳤다. 한 UPDATE로 올리고 그 반환값으로 판단하는
reserve-then-check로 바꿨다. 그런데 **일일·월간 캡은 그때 같이 안 고쳤다.** 이렇게 남아 있었다:

```python
if ai_usage.count_today(db, user_id) >= settings.ai_daily_cap:   # ① 읽고 판단
    raise HTTPException(429, ...)
...
markdown = generate_draft(...)                                    # ② LLM 호출 (수 초)
...
if provider == "claude":
    ai_usage.increment_today(db, user.id)                         # ③ 성공 뒤에 증가
```

`increment_today` 자체는 원자적이었다(`ON CONFLICT DO UPDATE`). 그래서 "원자적으로 고쳤다"고
기억하고 있었다. **틀렸다 — 원자적인 건 증가이고, 판단은 그 앞에서 따로 하고 있었다.**

그리고 이 결함이 시간당 캡의 것보다 나쁘다: 시간당 캡은 읽기와 증가가 붙어 있어 창이 밀리초였는데,
여기는 **읽기와 증가 사이에 LLM 호출이 들어 있다.** 훈련에서 실측한 창은 **3.0초**다.
공유 계정에 여러 IP로 몰리는 상황에서 3초는 짧지 않다.

시간당 캡(10, 원자적)이 상한을 걸어주긴 한다. 하지만 그건 "안전하다"가 아니라
**"시간당 캡만큼은 넘칠 수 있다"**는 뜻이다. 일일 캡의 실질 상한은 20이 아니라 최대 `20 + 9`였다.

### 고친 것

일일·월간도 시간당과 같은 reserve-then-check로 맞췄다(`_reserve_server_slot`).
먼저 원자적으로 +1 하고, 그 반환값으로 판단하고, 통과 못 하면 예약을 되돌린다(`decrement_today`).

성공만 센다는 기존 의도는 **되돌리기로 보존**했다 — 생성이 실패하면 예약을 취소한다.
취소는 실패 경로 셋(503·503·502)에 흩어놓지 않고 `finally` 한 곳에 뒀다. 하나만 빠뜨리면
사용자가 쓰지도 않은 한도를 잃는다.

`decrement_today`에는 `count > 0` 조건이 붙어 있다. 없으면 취소가 겹칠 때 카운트가 음수로
내려가고, **음수는 다음 요청에게 "한도에 여유가 있다"로 읽혀** 캡 자체가 무너진다.

### 같은 훈련을 그대로 재실행

```
  req code  elapsed(s)
  1 200 1.98
  2 429 0.09
  3 429 0.11
  4 429 0.11
  5 429 0.10

  200(실제 Anthropic 청구): 1건   429(차단): 4건
  ai_usage(일일).count   = 20   ← 캡 20
  일일 캡 초과분          = 0건  ✅ 캡 안
```

차단된 4건은 **0.1초 안에** 끝났다 — LLM 호출까지 가지 않았으므로 청구도 없다.

**월간 캡 경계도 따로 재봤다.** 이번 달 199/200에서 동시 5발 → 200 1건 + 429 4건,
월간 합계 정확히 200, 초과 0건. 메시지도 월간 문구로 나왔다.

## ② 예산 두 개가 같은 계정을 보며 $17.78과 $0.00을 보고하고 있었다 (안 고침 — 기록)

AWS Budgets에 예산이 두 개 있다. 둘 다 terraform 밖(콘솔 생성)이다.

| 예산 | 상한 | 실사용 | 알림 상태 |
|---|---|---|---|
| My Monthly Cost Budget | $10 / 월 | **$17.783 (178%)** | ACTUAL>85% **ALARM** · ACTUAL>100% **ALARM** · FORECASTED>100% OK |
| My Zero-Spend Budget | $1 / 월 | **$0.00** | ACTUAL>$0.01 **OK** |

같은 달, 같은 계정이다. 차이는 하나뿐이다 — **크레딧을 비용으로 세는가.**
Cost Explorer를 `RECORD_TYPE`으로 쪼개 확인했다:

```
Usage             17.7836033411
Credit           -17.7834727487
Bundled Discount  -0.0001312421
Tax                0
                 ─────────────
순액              ≈ 0.0000
```

Zero-Spend 예산은 `IncludeCredit: true`라 크레딧이 사용액을 상계해 $0.00으로 읽는다.
Monthly 예산은 크레딧을 빼지 않아 $17.78을 본다.

**왜 이게 나쁜가.** "쓸 의도가 없었는데 돈이 나가고 있다"를 잡는 게 Zero-Spend 예산의 존재
이유인데, 이 계정은 유한한 크레딧($60, 만료 2027-06-24)을 태우는 중이다. 즉 그 예산은
**정확히 그것이 필요한 기간 동안 반드시 침묵한다.** 크레딧이 0이 되는 순간에야 입을 연다.
06-25에 "청구서가 $0"과 "안 쓰고 있다"는 다르다는 걸 이미 배웠는데(PROGRESS.md), **그 교훈이
가드레일 설정에는 반영되지 않은 채 남아 있었다.**

한편 $10 예산은 **실제로 울렸다** — 85%·100% 둘 다 ALARM 상태다. 수신자는
`es0764@naver.com`. 그래서 이 훈련이 답한 것과 못 답한 것이 갈린다:

- 답함: 예산 알람은 **구성돼 있고 실제로 발동했다**(ALARM 상태로 증거가 남아 있다).
- **못 답함: 그 편지함을 사람이 보는가.** 07-20의 "설정했다 ≠ 동작한다"의 다음 단계 —
  **"발동했다 ≠ 사람에게 닿았다"**. 이건 코드로 증명할 수 없다.

## 비용

훈련에 쓴 실제 Anthropic 호출은 **7건**(하이쿠, 한 줄 메모): 수정 전 5 + 수정 후 1 + 월간 경계 1.
차단된 **10건**(수정 후 4 + 월간 4 + 재시작 2)은 LLM까지 가지 않아 무료다 — 그게 이 수정의
요점이기도 하다. 프로덕션 배포 후 라이브 확인 1건도 429라 무료였다. 센트 단위이고
AWS 리소스 변경은 예산 쪽 0건이다(읽기만 했다. Cost Explorer API는 요청당 $0.01).

## ④ 그 감시 자체를 검사했더니 거짓말을 하고 있었다 (수정함)

새로 넣은 watch.sh 6번에 장애를 주입해봤다. **감시가 틀리게 말하는 건 감시가 없는 것보다
나쁘다** — 없으면 모르는 줄 알지만, 틀리면 아는 줄 안다.

| 주입 | 처음 나온 말 | 사실 | 고친 뒤 |
|---|---|---|---|
| 자격증명 실패(=CI 역할에 권한 없음) | "예산을 못 읽었다" | 맞음 | 그대로 |
| **python3이 깨짐** | **"예산이 0개다 — 청구서 폭주를 알려줄 장치가 없다"** | **예산 2개 있었다** | python3을 경로에서 제거 |
| 목록은 읽히고 알림만 실패 | "ACTUAL 알림이 없다" | 못 읽은 것 | "알림 상태를 못 읽었다"로 분리 |
| 읽었는데 진짜 0개 | "예산이 0개다" | 맞음 | 그대로(위와 메시지가 달라야 하는 이유) |

두 번째가 특히 나쁘다. JSON 개수를 `python3`으로 셌는데 그 실패에 `|| echo 0`을 붙여둬서,
**해석기가 죽은 것이 "가드레일이 없다"는 사실 주장으로 승격**됐다. 07-22 SES 건(빈 값을
초록으로 보고)과 07-28 심층검사 건(증상 서술이 틀렸던 것)과 같은 병이다. 같은 병을 세 번째로
만든 셈이라, 이번엔 조건을 고치는 대신 **그 경로 자체를 없앴다** — CLI의 `--query`와 awk만
쓴다(둘 다 없으면 aws 호출이 애초에 안 되므로 '못 읽었다'로 정직하게 떨어진다).
