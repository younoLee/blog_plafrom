## 1. 기준선이 주입 전부터 502 였다 — 하네스

첫 기준선에서 **AI 초안 502 · 결제 confirm 502**. 주입 전이다.

blackhole 의 `pass` 모드는 어느 호스트에든 `{"ok":true,"chaos":"pass"}` 를 줬다. 08-27 까지는
그걸로 됐는데, 그 뒤 앱이 응답을 제대로 읽게 고쳐졌다.

| 경로 | 앱이 이제 보는 것 | 결과 |
|---|---|---|
| 결제 confirm | `status`·`totalAmount`·`orderId` 대조(`b3933ba`) | "필요한 필드가 없다" → 502 |
| AI 초안 | SDK 가 `content` 를 읽음 | `TypeError` → 502 |
| AI 초안(위를 고친 뒤) | ai_guard 가 `# 제목` 으로 시작하는지 | `schema_mismatch` → 422 |

**07-28 규칙(기준선 먼저)은 지켰는데 그 기준선이 거짓이었다.** 이대로 주입했으면 모든 칸이
'원래도 502, 주입해도 502'라 아무것도 판정하지 못한다. `blackhole.py` 의 `pass` 가 호스트마다
벤더 모양의 정상 응답을 주게 고쳤다(토스는 요청의 주문번호·금액을 되돌려줘 위변조 대조를
정상 통과). 고친 뒤 기준선은 AI 200 · 결제 200 이다.

부수: 파일을 고치면 단일 파일 바인드 마운트가 끊긴다(Docker Desktop, inode 교체).
`up.sh` 는 설정이 같으면 컨테이너를 안 바꾸므로 `chaos_dc up -d --force-recreate --no-deps blackhole`.

## 2. 잰 것

⚠️ **blackhole 모드는 호스트 구분 없이 전역이다.** `inject.sh anthropic hang` 은 토스·푸시·S3 도
같이 hang 시킨다. 그래서 아래는 '대상'이 아니라 **'모드'** 단위로 읽는다.

| 모드 | AI 초안 | 결제 confirm | 08-27 과 |
|---|---|---|---|
| refuse | **502** / 0.02초 → 고친 뒤 **503** / 0.06초 | 502 / 0.01초 | AI 만 달랐다(아래 3절) |
| hang | **502** / 55.08초 → 고친 뒤 **503** / 55.04초 | 502 / 15.02초 | AI 만 달랐다. 상한은 50초대 → 55초(REQUEST_TIMEOUT) |
| error(503) | 503 / 0.06초 | 502 / 0.05초 | 같다 |
| gone(410) | 502 / 0.07초 | 400 / 0.06초 | 같다 |

| 주입 | 결과 | 08-27 과 |
|---|---|---|
| smtp refuse·hang | 초대 발급 201 그대로(0.39~0.73초) | 같다(메일 실패를 막지 않음 — 유지된 선택) |
| db refuse | 503 `application/json` / 3.84초 | 같다 |
| db hang | 글 목록·작성 **503 / 5.01초** | **다르다 — 08-27 엔 240초 0바이트** (아래) |
| db hang → `/api/status` | t+5초 `ok`(직전 주기 값) → **t+70초 `down`** → t+130초 `down` | 08-27 고침이 유지된다(전엔 884초 `ok`) |
| 복구(`none`) | 전 경로 정상 | 같다 |

**db hang 이 5.01초에 끊긴다.** 08-27 문서는 "connect_timeout 은 새 커넥션에만 걸리고 pause 는
못 끊는다"고 적었다. 이번엔 요청이 5초에 503 이 됐다 — 풀의 기존 커넥션이 아니라 **새 커넥션의
시작 핸드셰이크**에서 `connect_timeout=5` 가 걸린 것으로 보인다(5.01 이 그 값이다). 다만 이미
쥐고 있던 커넥션에서 쿼리 도중 얼면 어떤지는 이번에도 안 쟀다. "상한이 생겼다"고 일반화하지 않는다.

## 3. 새로 나온 것 — AI 업스트림 분류가 10-17 부터 깨져 있었다 (high, 고침)

refuse·hang 에서 AI 가 08-27 의 503 이 아니라 502 "키/모델명 확인 후 다시 시도" 였다.

원인: anthropic 1.x · openai 3.x 가 운송 계층을 **`httpx2`** (별도 패키지)로 바꿨다.
`routers/ai.py` 의 `_upstream_unreachable` 은 예외 사슬에서 `httpx.TransportError` 만 찾는데,
`httpx2.ConnectError` 는 그 하위 타입이 아니다. 컨테이너에서 실제 SDK 로 재현:

```
0 anthropic APIConnectionError
1 httpx2    ConnectError
2 httpcore2 ConnectError
3 builtins  ConnectionRefusedError
unreachable= False
```

- 들어온 날: **10-17 `407aee7`**(Dependabot 백엔드 업데이트 수용). **10-25 배포로 운영에 나갔다.**
- 왜 시험이 못 잡았나: 기존 시험 넷이 전부 httpx 예외를 **손으로 만들어** 넣는다. 손으로 만든
  예외는 '오늘 SDK 가 실제로 던지는 것'을 대변하지 못한다.
- 고침: httpx2 의 `TimeoutException`·`TransportError` 도 본다. 시험은 **실제 SDK 를 닫힌 포트로
  불러** 그 예외로 판정한다(anthropic·openai). 고침을 빼면 두 칸 다 빨갛다 — 확인했다.
- 재주입: refuse 503 / 0.06초 · hang 503 / 55.04초, 로그는 "AI 업스트림 장애".

**같은 가정에 기대는 곳을 더 봤다:** `services/ai.py` 가 openai 에 SSRF 방어용 `httpx.Client
(follow_redirects=False)` 를 넘긴다. httpx2 로 바뀐 SDK 가 그걸 무시하면 방어가 조용히 꺼진다.
302 를 주는 로컬 서버로 재봤다 — 요청 1회, 302 에서 멈췄다. **방어는 살아 있다.** 손대지 않았다.
