lockfile 은 손으로 고쳤다(이 기계 npm 이 `allow-remote=none`). 셋으로 대조했다 —

## 4. 훈련이 낸 두 줄은 둘 다 결함이 아니었다

- **`FAIL keep/latest.sql.gz 가 최신 덤프보다 오래됐습니다 — 승격이 실패한 채 남아 있습니다`**
  → 09-10 승격은 정상으로 돌았다. `keep/latest.sql.gz` 가 573,431 B · 09-10 16:34:23 이고
  3초 전 올라간 `blog-2026-09-10-0734.sql.gz` 가 같은 573,431 B 다. 진짜 원인은 **순서**다 —
  승격은 정지 절차 3/6 이고, 훈련의 권장 시점은 '켜진 동안'이다. 그 사이
  `deploy_backend.sh` 가 백업을 하나 뜨므로 **회차 중간에는 keep/ 가 반드시 뒤처진다.**
  즉 이 검사는 권장 시점에 돌리면 **항상 FAIL 한다.**
- **`WARN 참조 이미지 1개 중 1개가 없습니다 → 그 글은 지금도 이미지가 깨져 있습니다`**
  → 깨진 글은 없다. 그 `uploads/.wtest` 는 개발일지 #28 본문이 인용한 터미널 한 줄이다
  (`content/devlog/2026-08-10.md:308` — uid 10001 이 `uploads/` 에 못 쓰던 대목의
  `touch … → Permission denied`). 추출기가 본문 산문에서 `uploads/...` 를 긁어 센 것이다.

공교롭게 같은 날 세 번째 사례가 하나 더 있었다 — 이 회차에서 띄운 CI 감시 스크립트가
jobs API 의 `in_progress`(정확히는 `conclusion: null`)를 `!= "success"` 로 보고
`FAIL` 로 찍었다. run 자체는 `success` 였다.

**셋 다 '아직 아니다'와 '인용했다'를 '깨졌다'로 읽은 것이다.** 이 저장소가 반복해 잡아온
"검사가 자기 대상을 안 본다"의 거울상이다 — 이쪽은 **대상을 보긴 하는데 잘못 읽는다.**
